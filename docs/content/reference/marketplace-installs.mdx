# Marketplace Installs

ark-api can install a marketplace item into the current namespace on behalf of the dashboard user. The install runs as a dedicated `ark-marketplace-installer` ServiceAccount, which exists only in namespaces where the platform team has enabled the feature through the `marketplaceInstall` values of the `ark-tenant` chart.

The installer ServiceAccount is a namespace admin. Anyone allowed to start an install can make a chart grant them lasting permissions in the namespace, so treat the permission below as namespace admin.

## Who may install

Installing requires `create` on the `marketplaceinstalls` resource in the `ark.mckinsey.com` API group, in the target namespace. There is no `marketplaceinstalls` CRD: the name exists only for RBAC, and ark-api checks it with a SelfSubjectAccessReview made as the signed-in user.

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: marketplace-installer
  namespace: team-a
rules:
  - apiGroups: ["ark.mckinsey.com"]
    resources: ["marketplaceinstalls"]
    verbs: ["create"]
```

Reading install state requires `list` on `jobs` or the `create` permission above. Install logs additionally require `get` on `pods/log`.

Installs need a user identity:

| Authentication | Behaviour |
| --- | --- |
| `AUTH_MODE=open` (or unset) | No user check. |
| API key | Refused with `api-key-not-supported`. |
| `sso` or `hybrid` with impersonation disabled | Refused with `impersonation-disabled`. |
| `sso` or `hybrid` with impersonation enabled | SelfSubjectAccessReview as the user. Any error during the review counts as a deny. |

## ark-api endpoints

| Method | Path | Purpose |
| --- | --- | --- |
| `GET` | `/api/v1/namespaces/{namespace}/marketplace-installs/capability` | Whether the current user can install in the namespace, and why not. |
| `POST` | `/api/v1/namespaces/{namespace}/marketplace-installs/{item}/preview` | What installing an item would create, and whether anything blocks it. |
| `POST` | `/api/v1/namespaces/{namespace}/marketplace-installs/{item}` | Start installing an item that was just previewed. |
| `GET` | `/api/v1/namespaces/{namespace}/marketplace-installs` | The install state of every release in the namespace. |
| `GET` | `/api/v1/namespaces/{namespace}/marketplace-installs/{item}?source=` | The install state of one item, with its events and log. |

### Capability

The response is always HTTP 200:

```json
{"enabled": false, "reason": "namespace-not-enabled"}
```

`reason` is `null` when `enabled` is `true`. Otherwise it is the first of these that applies:

| Reason | Meaning |
| --- | --- |
| `read-only` | ark-api runs with `READ_ONLY_MODE=true`. |
| `api-key-not-supported` | The request was authenticated with an API key. |
| `impersonation-disabled` | User impersonation is disabled on ark-api. |
| `namespace-not-enabled` | The installer ServiceAccount is missing, ark-api cannot impersonate it, or it cannot create Jobs. |
| `policy-missing` | Neither `ark-marketplace-installer-sa-<namespace>` nor its `-bootstrap` copy is a ValidatingAdmissionPolicy and binding pair that protects the installer ServiceAccount. A pair counts when the binding is in `Deny` mode, points at the policy of the same name, and has no resource rules, exclusions or object selector. The policy must have `failurePolicy: Fail` and no exclusions or object selector, and both namespace selectors must cover the namespace. |
| `not-permitted` | The request has no user identity, or the user lacks `create` on `marketplaceinstalls`. |

A request without a user identity gets `not-permitted` right after the API key and impersonation checks, before the namespace checks. In open mode, `read-only`, `namespace-not-enabled` and `policy-missing` still apply.

The `policy-missing` check reads how the policy and binding are matched, not their `validations` or `matchConditions`. Creating or changing a ValidatingAdmissionPolicy needs cluster admin rights, so only a cluster admin can weaken it. When a pair does not count, ark-api logs the reason at info level.

The namespace must be a valid Kubernetes namespace name. Any other value returns HTTP 422.

The capability only tells the dashboard what to show. Every install endpoint repeats the user check.

### Preview

```json
POST /api/v1/namespaces/team-a/marketplace-installs/phoenix/preview
{"source": "official"}
```

`source` is the name of an entry in the namespace's `marketplace-sources` ConfigMap and `item` is the `name` of an item in that source's catalogue. The request never carries a chart reference: ark-api resolves it from the catalogue, so editing the catalogue is the only way to change what gets installed. Anyone who can edit the namespace's marketplace sources therefore decides what installers are offered, which is why the preview shows the source, the chart reference and the digest.

An `item` or `source` that is not a valid name returns HTTP 422 with FastAPI's validation error body, before any check.

A preview runs these steps and stops at the first failure:

1. The user check above.
2. The installer ServiceAccount and its admission policy must be in place, as for `namespace-not-enabled` and `policy-missing` in the capability.
3. ark-api reads the source and its credential as the signed-in user, fetches the catalogue (always fresh, never from the items cache) and finds the item. In open mode it reads them with its own ServiceAccount, so previews only work in namespaces where that ServiceAccount can read the `marketplace-sources` ConfigMap and the sources' credential Secrets. Since the tenant chart refuses to enable installs in ark-api's own namespace, that takes extra RBAC in the tenant namespace.
4. Installing is opt-in: the item must set `ark.installable: true` (a boolean), and an `ark.chartPath` that starts with an allowed registry prefix (see Configuration), followed by a single chart name. Items without `ark.installable: true` stay on the copy-the-command path. The release name is `ark.helmReleaseName`, or the item name when it is missing, and must be a valid Helm release name. `installArgs` and `ark.namespace` are ignored.
5. If the item's release is already in the namespace, the preview stops with `already-installed` and returns the install record (see Install state): an item can only be previewed while it is `installable`.
6. ark-api runs `helm pull` for the latest chart version, which pins the digest, then `helm template --include-crds`. The chart must be downloadable without credentials.
7. Every rendered object, hooks included, gets one verdict.

The whole preview must finish within `MARKETPLACE_INSTALL_PREVIEW_TIMEOUT_SECONDS` (25 by default), otherwise it fails with `preview-timeout` and helm is stopped. ark-api runs at most two helm processes at a time.

Each object gets the first verdict that applies. Every verdict except `free` blocks the install.

| Verdict | Meaning |
| --- | --- |
| `crd` | The object is a CustomResourceDefinition. |
| `cluster-scoped` | The object is cluster-scoped. Installs are limited to the namespace. |
| `namespace-mismatch` | The object names a namespace other than the target. |
| `skip-webhook-label` | The object carries `ark.mckinsey.com/skip-webhook-validation`. |
| `rbac-escalation` | A Role with rules on `rbac.authorization.k8s.io`, a `*` group, verb or resource, a wildcard subresource (`*/exec`, `pods/*`), any access to Secrets, `pods/exec`, `pods/attach`, `pods/ephemeralcontainers`, `serviceaccounts/token`, `impersonate`, `escalate` or `bind`; a RoleBinding to anything but a Role rendered by the same chart, or to a subject outside the namespace, a Group or a `system:` user; or any use of the `ark-marketplace-installer` ServiceAccount. |
| `reserved-secret` | A Secret with a name reserved for personal Secrets (`u-<16 hex>-…`) or an `ark.mckinsey.com/scope` label other than `shared`. |
| `personal-secret-ref` | The object references a Secret with a reserved name, or an existing Secret labelled as personal, through `secretKeyRef`, any field ending in `secretRef` (such as `envFrom`, `tokenSecretRef` or a CSI `nodePublishSecretRef`), `secretName`, a projected volume or `imagePullSecrets`. |
| `unverifiable` | The cluster has no single resource for the kind (not served, ambiguous, or a `List`), the object has no fixed name, the API server could not be reached, the installer ServiceAccount cannot read it, a referenced Secret could not be checked, or the API server rejected the dry run for a reason other than Pod Security. |
| `conflict-release` | The object already exists and belongs to a Helm release, named in `ownedByRelease`. |
| `conflict-unmanaged` | The object already exists and no Helm release owns it. |
| `psa-violation` | A server-side dry run of the object reports a Pod Security warning or rejection for the namespace. |
| `free` | The object does not exist yet and passed every check. |

The existence checks and dry runs run as the installer ServiceAccount. Objects in the `ark.mckinsey.com` group are never dry run, because Ark's API server stores objects even when a dry run is requested. Other aggregated API servers are dry run like any other kind, so a chart should not include kinds from an aggregated API that ignores `dryRun`.

```json
{
  "source": "official",
  "itemName": "phoenix",
  "chartName": "phoenix",
  "chartRef": "oci://ghcr.io/mckinsey/agents-at-scale-marketplace/charts/phoenix",
  "chartVersion": "0.1.12",
  "digest": "sha256:…",
  "releaseName": "phoenix",
  "namespace": "team-a",
  "blocked": false,
  "expiresAt": "2026-11-19T12:10:00Z",
  "resources": [
    {"apiVersion": "apps/v1", "kind": "Deployment", "name": "phoenix", "namespace": null, "state": "free", "ownedByRelease": null, "hook": false, "message": null}
  ]
}
```

ark-api keeps the result in memory until `expiresAt`, keyed by namespace, source, item and digest. It stores only the identity of each object and the outcome, never the rendered manifest. The cache lives in the ark-api pod, so a restart clears it.

### Install

```json
POST /api/v1/namespaces/team-a/marketplace-installs/phoenix
{"source": "official", "digest": "sha256:…"}
```

`digest` is the one the preview returned. A request runs these steps within `MARKETPLACE_INSTALL_POST_TIMEOUT_SECONDS` (20 by default):

1. The user check, and the installer ServiceAccount and admission policy checks, as for the preview.
2. ark-api resolves the item from the catalogue again and reads its install state. An item that is already `installing` returns 202 with its record; any other state but `installable` returns `already-installed`.
3. The preview must still be in memory for that namespace, source, item and digest, and its chart reference and release name must match the catalogue now. Otherwise the request fails with `preview-expired`, and the client has to run the preview again. A blocked preview fails with `preview-blocked`. Because the preview cache is not tied to a user, this is why step 1 runs again: a preview someone else made does not let you install.
4. ark-api takes the install lock of the namespace, a Lease named `marketplace-install-lock` that it creates with its own ServiceAccount. Only one install runs per namespace: while another item's Job runs, or its Lease is younger than `MARKETPLACE_INSTALL_LOCK_STALE_SECONDS` and has no Job yet, the request fails with `another-install-active` and names that release.
5. It deletes a completed install Job of the item whose release is gone, and checks that none of the previewed objects has appeared since the preview (`conflicts-changed`).
6. It creates the install Job as the installer ServiceAccount and records a `MarketplaceInstallStarted` event on it.

The response is 202 with the install record. When the time limit passes the response is 503 `busy`, which does not mean nothing started: the Job may have been created, and the install state shows it.

The Job runs the ark-api image as the installer ServiceAccount, with a read-only root filesystem and a restricted security context:

```bash
timeout -k 10 --signal=TERM 660 helm install <release> <chartRef>@<digest> --namespace <namespace> --wait --timeout 600s --skip-crds [--plain-http] [--description installed-by=<user>]
```

`--plain-http` is added for registries listed in `MARKETPLACE_INSTALL_PLAIN_HTTP_REGISTRIES`, and `--description` names the signed-in user (not in open mode). The chart is installed by digest, so it is the one the preview rendered. Helm never runs `upgrade`, never takes ownership of existing objects and never gets values. When the outer `timeout` stops helm, the Job fails through its pod failure policy and the install is `timed-out`. Jobs are not deleted automatically, so their status and log stay available.

The lock counts as free once the Job of the item that holds it has finished, or when its holder has no Job and the Lease is older than `MARKETPLACE_INSTALL_LOCK_STALE_SECONDS`. ark-api deletes it only when a request fails before creating the Job; after a lost connection it keeps it, because the Job may exist. The admission policy lets only ark-api's ServiceAccount create, change or delete that Lease. To release a lock that has no install Job before it goes stale, delete it as that ServiceAccount:

```bash
kubectl delete lease marketplace-install-lock -n <namespace> --as=system:serviceaccount:<ark-api-namespace>:ark-api-sa
```

Never remove the admission policy binding to do this: the same policy keeps everyone else from running workloads as the installer ServiceAccount.

### Install state

```http
GET /api/v1/namespaces/team-a/marketplace-installs
GET /api/v1/namespaces/team-a/marketplace-installs/phoenix?source=official
```

ark-api stores no install state. Each request derives it from the install Job and the Secrets that Helm writes for every revision of a release, so a refresh, another tab or another user see the same state, and a release installed with the Helm CLI is reported too. Both requests need the read permission described in Who may install, and read the namespace as the installer ServiceAccount.

The list returns one record per release that has an install Job or a Helm release Secret in the namespace, including releases that did not come from the marketplace, such as the `ark-tenant` chart itself. Records of releases without an install Job have no `source` or `itemName`; match them to catalogue items by `ark.helmReleaseName`. The list carries no events or logs, so it is cheap enough to poll.

The single record looks up the install Job of that source and item first. Without one, it resolves the item from the catalogue to learn its release name, and returns the catalogue errors of the preview when that fails. It adds the Kubernetes events of the install Job, its pods and the ReplicaSets of the release's Deployments (at most 20, newest first), and for `installing`, `failed` and `timed-out` the last 100 lines (16 KiB at most) of the install log, with control characters removed and credentials redacted. The log is returned only to users who may `get` `pods/log` in the namespace.

```json
{
  "source": "official",
  "itemName": "phoenix",
  "release": "phoenix",
  "chartVersion": "0.1.12",
  "digest": "sha256:…",
  "state": "failed",
  "stage": null,
  "failedStage": "apply",
  "startedAt": "2026-11-19T12:01:00Z",
  "installedBy": "alice@example.com",
  "events": [
    {"type": "Warning", "reason": "BackOff", "message": "…", "objectKind": "Pod", "objectName": "…", "count": 3, "lastSeen": "2026-11-19T12:03:00Z"}
  ],
  "log": "Error: …"
}
```

| State | Meaning |
| --- | --- |
| `installable` | No install Job and no release, or a completed Job whose release was uninstalled. |
| `installing` | The install Job is running. `stage` is `resolve` before its pod runs and `apply` while helm runs, including while it waits for the chart's resources to become ready. `ready` appears only in the short window after Helm marks the release deployed and before the Job completes. |
| `installed` | The release is deployed at revision 1. |
| `failed` | The install Job failed, or the release failed without a Job. `failedStage` is `resolve` when no release was created, `apply` otherwise. |
| `timed-out` | The install ran out of time: the outer timeout, the Job deadline, or a release that failed with a deadline error. `failedStage` is `ready`. |
| `platform-managed` | The release was upgraded or rolled back (revision above 1), or is being uninstalled. The dashboard leaves it to the platform team. |

`failed` and `timed-out` are final: the platform team cleans up before the item can be installed again.

Treat events and release Secrets as untrusted input. Anyone who may create Secrets or events in the namespace can forge them, directly or through a workload running with a ServiceAccount that has those rights, such as an Argo Workflow, an agent tool or an installed chart; the Ark API itself offers no way to do so. A forged release Secret can only misreport state in its own namespace, and ark-api caps how much of a release payload it decompresses. Install Jobs and their pods are trusted only when they run as the installer ServiceAccount, which the admission policy reserves for ark-api, so both state requests also require the policy to be in place.

## Configuration

These ark-api environment variables are set in `services/ark-api/chart/values.yaml`.

| Variable | Default | Purpose |
| --- | --- | --- |
| `MARKETPLACE_INSTALL_REGISTRY_ALLOWLIST` | `oci://ghcr.io/mckinsey/agents-at-scale-marketplace/charts/` | Comma-separated chart registry prefixes. Each must start with `oci://` and end with `/`; entries that don't are ignored with a warning. An empty list allows nothing. |
| `MARKETPLACE_INSTALL_PLAIN_HTTP_REGISTRIES` | empty | Comma-separated `host:port` registries reached over plain HTTP, for test registries. |
| `MARKETPLACE_INSTALL_PREVIEW_TIMEOUT_SECONDS` | `25` | Limit for a whole preview. |
| `MARKETPLACE_INSTALL_PREVIEW_CACHE_SECONDS` | `600` | How long a preview stays valid. |
| `MARKETPLACE_INSTALL_PREVIEW_CACHE_MAX_ENTRIES` | `256` | Previews kept in memory; the oldest goes first. |
| `MARKETPLACE_INSTALL_POST_TIMEOUT_SECONDS` | `20` | Limit for an install request. |
| `MARKETPLACE_INSTALL_HELM_TIMEOUT_SECONDS` | `600` | `--timeout` of `helm install --wait`. |
| `MARKETPLACE_INSTALL_TOTAL_TIMEOUT_SECONDS` | `660` | Outer limit of the helm process in the Job; reaching it gives `timed-out`. |
| `MARKETPLACE_INSTALL_JOB_DEADLINE_SECONDS` | `900` | `activeDeadlineSeconds` of the install Job, with room for pulling the image. |
| `MARKETPLACE_INSTALL_LOCK_STALE_SECONDS` | `30` | Age after which a lock whose holder has no Job is taken over. |
| `MARKETPLACE_INSTALL_IMAGE` | the ark-api image | Image of the install Job. The chart sets it to ark-api's own image and tag. |
| `MARKETPLACE_INSTALL_IMAGE_PULL_SECRETS` | empty | Comma-separated pull Secrets for that image, in the tenant namespace. |

ark-api needs network access to the allowed registries. The chart download is capped at 10 MiB and the rendered output at 2 MiB, 300 objects and 64 levels of nesting; the size of the download is checked once it has finished, so the timeout is what bounds a slow or oversized download.

## Errors

Install endpoints return errors in this shape:

```json
{"detail": {"code": "not-permitted", "message": "You are not permitted to install marketplace items in this namespace"}}
```

The user check returns HTTP 403 with `code` set to `api-key-not-supported`, `impersonation-disabled` or `not-permitted`. An error about an item that is already present also carries its install record in `detail.record`. The preview can also return:

| Status | Code | Meaning |
| --- | --- | --- |
| 404 | `source-not-found` | The namespace has no marketplace sources, or none with that name. |
| 404 | `item-not-found` | The source's catalogue has no item with that name. |
| 409 | `namespace-not-enabled` | Installs are not enabled in the namespace. |
| 409 | `policy-missing` | The admission policy that protects the installer ServiceAccount is missing. |
| 409 | `already-installed` | The item's release is already installing, installed, failed, timed out or managed by the platform team. `detail.record` holds its state. |
| 422 | `not-installable` | The item does not set `ark.installable: true`, has no chart, or has an invalid release name. |
| 422 | `registry-not-allowed` | The item's chart is not on an allowed registry. |
| 422 | `render-failed` | `helm template` failed or its output exceeded the limits. |
| 502 | `catalog-unavailable` | The marketplace sources or the source's credential cannot be read, or the catalogue could not be fetched. |
| 502 | `chart-unavailable` | `helm pull` failed. The message names the registry. |
| 504 | `preview-timeout` | The preview did not finish in time. |

The install request can also return:

| Status | Code | Meaning |
| --- | --- | --- |
| 409 | `already-installed` | The item's release is installed, failed, timed out or managed by the platform team. |
| 409 | `preview-expired` | No matching preview in memory, or the catalogue changed since the preview. |
| 422 | `preview-blocked` | The preview found objects that block the install. |
| 409 | `another-install-active` | Another item is being installed in the namespace. |
| 409 | `conflicts-changed` | An object of the preview exists now, or could not be checked. |
| 409 | `foreign-job` | A Job with the install Job's name exists and ark-api did not create it. |
| 502 | `cluster-error` | A Kubernetes request of the install failed. The message names the status, never the response body. |
| 503 | `busy` | The request ran out of time, or the item's previous install Job is still being deleted. |
| 500 | `install-misconfigured` | ark-api has no image configured for install Jobs. |

A request body that fails validation returns 422 with FastAPI's validation body, a list in `detail`, as for the other endpoints.

The state requests return the user check errors, `namespace-not-enabled` and `policy-missing` as for the preview, and for a single record without an install Job the catalogue errors above.
