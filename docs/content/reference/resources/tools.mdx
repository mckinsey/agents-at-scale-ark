# Tool

A `Tool` is a callable an agent can invoke: an HTTP endpoint, a function on an MCP server, another agent or team, a built-in, or an inline script. For a task-oriented walkthrough see [User Guide → Tools and MCP servers](/user-guide/tools); this page is the field-by-field reference.

## Spec

Every `Tool` has a `type`, an optional `description` and `inputSchema`, and exactly one type-specific block matching the `type`. A complete example (HTTP):

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Tool
metadata:
  name: example-tool
spec:
  # Required: one of http | mcp | agent | team | builtin | inline
  type: http

  # Description the LLM reads to decide when to call the tool
  description: "What this tool does"

  # JSON Schema describing the arguments the LLM must supply
  inputSchema:
    type: object
    properties:
      city:
        type: string
    required: ["city"]

  # Optional MCP-style hints
  annotations:
    readOnlyHint: true
    title: "Get coordinates"

  # The type-specific block (http here). For other types use mcp / agent /
  # team / builtin instead — see the sections below.
  http:
    url: https://geocoding-api.open-meteo.com/v1/search?name={city}&count=1
    method: GET
    timeout: 30s
```

The type-specific block must match `type`: `http` → `spec.http`, `mcp` → `spec.mcp`, `agent` → `spec.agent`, `team` → `spec.team`, `builtin` → `spec.builtin`, `inline` → `spec.inline`. Each is documented below.

## Fields

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `spec.type` | enum (`http`, `mcp`, `agent`, `team`, `builtin`, `inline`) | yes | Which kind of tool this is. Drives which type-specific block is required. |
| `spec.description` | string | no | Shown to the LLM as the tool description. Drives whether the model calls it. |
| `spec.inputSchema` | JSON Schema | no | Schema for the arguments the LLM supplies. Validated as JSON Schema by the admission webhook. |
| `spec.annotations` | object | no | MCP-style hints: `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`, `title`. |
| `spec.http` | object | for `http` | HTTP request config (see [HTTP tools](#http-tools)). |
| `spec.mcp` | object | for `mcp` | Reference to a function on an MCP server (`mcpServerRef` + `toolName`). |
| `spec.agent` | object | for `agent` | `{ name }` of the Agent to wrap. |
| `spec.team` | object | for `team` | `{ name }` of the Team to wrap. |
| `spec.builtin` | object | for `builtin` | `{ name }` — must be `terminate` or `noop`. |
| `spec.inline` | object | for `inline` | `{ source, language }` — a short script (see [Inline tools](#inline-tools)). |

`status.state` is `Ready` with message `Tool configuration is valid` when the tool is usable. Inline tools also report a single `Available` condition and `status.resolvedAddress`; see [Inline tools](#inline-tools).

The `Tool` CRD defines no custom print columns, so `kubectl get tools` shows only `Name` and `Age`; use `kubectl describe tool <name>` or `-o yaml` to see `status.state`.

## HTTP tools

HTTP API calls with two distinct templating syntaxes:

- **URL parameters** — single braces `{name}`, substituted from the tool-call arguments and URL-encoded.
- **Body templates** — Go template syntax: `{{.input.fieldName}}` for arguments, `{{.paramName}}` for `bodyParameters`.

### GET

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Tool
metadata:
  name: get-coordinates
spec:
  type: http
  description: "Returns coordinates for the given city name"
  inputSchema:
    type: object
    properties:
      city:
        type: string
        description: City name to get coordinates for
    required: ["city"]
  http:
    url: https://geocoding-api.open-meteo.com/v1/search?name={city}&count=1
    method: GET
    timeout: 30s
```

### POST with body template

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Tool
metadata:
  name: create-user
spec:
  type: http
  description: "Creates a new user"
  inputSchema:
    type: object
    properties:
      name: { type: string }
      email: { type: string }
    required: ["name", "email"]
  http:
    url: https://api.example.com/users
    method: POST
    headers:
      - name: Content-Type
        value:
          value: application/json
    body: |
      {
        "name": "{{.input.name}}",
        "email": "{{.input.email}}",
        "created_at": "{{.timestamp}}",
        "organization": "{{.default_org}}"
      }
    bodyParameters:
      - name: timestamp
        value: "2024-01-01T00:00:00Z"
      - name: default_org
        valueFrom:
          configMapKeyRef:
            name: user-config
            key: default-organization
    timeout: 30s
```

### `http` fields

| Field | Required | Description |
| --- | --- | --- |
| `url` | yes | Endpoint. Must match `^https?://.*`. URL `{param}` placeholders are filled from the tool-call arguments. |
| `method` | no | `GET` (default), `POST`, `PUT`, `DELETE`, `PATCH` (also `HEAD`/`OPTIONS`). |
| `headers[]` | no | List of `{ name, value }`. Each `value` is either an inline `value`, or a `valueFrom` with a `configMapKeyRef` or `secretKeyRef`. |
| `timeout` | no | Per-request timeout, e.g. `30s`. |
| `body` | no | Go-template body for POST/PUT/PATCH. `{{.input.x}}` = arguments; `{{.name}}` = `bodyParameters`. |
| `bodyParameters[]` | no | Values for the body template: inline `value`, or `valueFrom` (`configMapKeyRef` / `secretKeyRef`). |

## MCP tools

Tools provided by a Model Context Protocol server. **These are normally auto-created** by the MCP server controller — when you apply an `MCPServer`, Ark discovers the functions it advertises and creates one `Tool` per function, named `<mcp-server>-<tool>` and labelled `mcp/server: <server>`. You rarely write these by hand. The generated shape:

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Tool
metadata:
  name: filesys-server-read-file
  labels:
    mcp/server: filesys-server
spec:
  type: mcp
  description: "Read contents of a file"
  inputSchema:
    type: object
    properties:
      path: { type: string }
    required: ["path"]
  mcp:
    mcpServerRef:
      name: filesys-server
      namespace: default
    toolName: read_file
```

## Agent and team tools

Wrap an Agent or Team so another agent can call it as a tool. Invoked with a single `input` argument.

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Tool
metadata:
  name: call-research-agent
spec:
  type: agent
  description: "Delegate a research question to the research agent"
  inputSchema:
    type: object
    properties:
      input: { type: string }
    required: ["input"]
  agent:
    name: research-agent
---
apiVersion: ark.mckinsey.com/v1alpha1
kind: Tool
metadata:
  name: research-team-tool
spec:
  type: team
  description: "Hand a topic to the research team"
  inputSchema:
    type: object
    properties:
      input: { type: string }
    required: ["input"]
  team:
    name: research-team
```

## Built-in tools

System functions implemented inside Ark. The `ark-tenant` chart seeds them as `Tool` resources, so on a standard install they already exist and you reference them by name. The set of built-ins is fixed in Ark's code — `terminate` and `noop`. The seeded shape:

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Tool
metadata:
  name: terminate
spec:
  type: builtin
  description: "Terminates the conversation"
  inputSchema:
    type: object
    properties:
      response:
        type: string
        description: The response to send before terminating
    required: ["response"]
  builtin:
    name: terminate
```

| Built-in | Behaviour |
| --- | --- |
| `terminate` | Ends the conversation / team turn with a final response. |
| `noop` | Does nothing and returns success — useful for testing and debugging. |

## Inline tools

An inline tool carries its own script in the resource. The script is run by an Ark-managed runner rather than an endpoint you host.

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Tool
metadata:
  name: word-count
spec:
  type: inline
  description: "Counts the words in the supplied text"
  inputSchema:
    type: object
    properties:
      text: { type: string }
    required: ["text"]
  inline:
    language: python
    source: |
      import json, sys
      args = json.loads(sys.argv[1])
      print(len(args["text"].split()))
```

### `inline` fields

| Field | Required | Description |
| --- | --- | --- |
| `source` | yes | Script body. Must be non-empty and at most 65536 UTF-8 bytes — use an [MCPServer](/reference/resources/mcpserver) for anything larger. |
| `language` | yes | Interpreter: `bash`, `python`, `node`, or `ts`. No default, and shebang lines are not used to pick one. |

An inline tool must not also set `spec.http`, `spec.mcp`, `spec.agent`, `spec.team`, or `spec.builtin`, and `spec.inline` is rejected on any other type. A tool cannot be converted between `inline` and another type — delete and recreate it instead.

### Runtime contract

The runner invokes the interpreter directly with the script path and the call arguments as **one JSON object in a single argument**. There is no shell, so quotes, newlines and metacharacters in the arguments are data, never commands.

| Language | Interpreter and image | Script path | Arguments |
| --- | --- | --- | --- |
| `bash` | `ark-inline-runner-bash` (Alpine, with `bash`, `jq` and coreutils) | `/tool/source.sh` | `$1` |
| `python` | `ark-inline-runner-python` (distroless Python 3) | `/tool/source.py` | `sys.argv[1]` |
| `node` | `ark-inline-runner-node` (distroless Node 24) | `/tool/source.js` | `process.argv[2]` |
| `ts` | `ark-inline-runner-node` — Node strips the types itself | `/tool/source.ts` | `process.argv[2]` |

Write the result to stdout. Limits are fixed and not configurable:

| Limit | Value |
| --- | --- |
| Request body | 128 KiB |
| Serialized arguments | 64 KiB, must be a JSON object |
| stdout returned | 256 KiB of valid UTF-8, truncated on a character boundary with a notice |
| stderr in an error | last 4 KiB |
| Execution | 30 seconds, or the caller's remaining budget if shorter |
| Resources | 50m CPU / 64Mi requested, 500m CPU / 256Mi limit |

A non-zero exit, a timeout, cancellation, or stdout that is not valid UTF-8 is reported to the model as a tool error with bounded stderr. Only `bash` has a shell; the other images have none.

**Only the standard library is available.** There is no package installation, no image override, and no network access from a runner. A script importing a third-party package fails at execution — move that tool to an [MCPServer](/reference/resources/mcpserver), which is also where anything needing files, credentials, or outbound calls belongs. TypeScript is limited to erasable syntax (no `enum`, `namespace`, or parameter properties), because Node strips types rather than compiling them.

### Status

| Field | Value |
| --- | --- |
| `status.state` | `Pending` until the tool is usable, then `Ready`. |
| `status.conditions[type=Available]` | `True` (reason `Available`) when callable, otherwise `False` with reason `RuntimeNotInstalled`, `ConflictingNetworkPolicy`, `ActivatorUnavailable`, or `ProvisioningFailed`. |
| `status.resolvedAddress` | Internal activator address. Only meaningful while `Available` is `True` for the current `metadata.generation`. |

With the feature enabled, the controller provisions the tool's runner: a source ConfigMap, a ServiceAccount with no mounted token, a deny-egress NetworkPolicy, a ClusterIP Service and a Deployment that starts at **zero replicas**. `Available: True` means the endpoint and current configuration are usable — not that a pod is running.

**Calls are not served yet.** The activator that fronts the runners is not part of this release, so an inline tool reports `Available: False` with reason `ActivatorUnavailable` once its runner exists, and `RuntimeNotInstalled` while `inlineTools.enabled` is false. Editing source updates the ConfigMap in place and rolls the pod template; a runner verifies the checksum of its mounted snapshot at startup and refuses to serve a revision other than the one it was created for.

### Runner process cleanup

The Linux runner execution core starts each call in its own process group and kills that group on completion, timeout, or cancellation. Before the interpreter starts, an inherited seccomp filter denies `setsid` and `setpgid` with `EPERM`. Python reports the error; runtimes such as Node may ignore it when asked to spawn a detached child, but that child remains in the call's process group. Ordinary subprocesses, pipelines, and background jobs remain supported, but cannot outlive the call.

The filter requires Linux amd64 or arm64 and needs no added capabilities. If it cannot be installed, the script does not run. Non-Linux execution is for local development only and does not provide this filter; process cleanup is not hostile-author isolation or a replacement for administrator-managed PID limits.

### Enabling inline authoring

Inline authoring is off by default and fails closed. Enable it per install:

```yaml
# ark chart values.yaml (and, in apiserver mode, the ark-apiserver chart)
inlineTools:
  enabled: true
```

The chart renders this as `ARK_INLINE_TOOLS_ENABLED` on the controller and the API server. Both write paths check it independently, so on the PostgreSQL backend set it in both charts or writes are denied by whichever path is still disabled.

Enabling requires an enforceable admission path. On the `etcd` backend, `webhook.enable` must be `true` — the chart fails to render otherwise, rather than installing a cluster where the schema accepts inline source that nothing authorises. On the `postgresql` backend the embedded API server enforces it in-process.

### Authorization

Every inline create and every inline spec update is checked with a `SubjectAccessReview` for the verb `use` on the virtual resource `inlinetools.ark.mckinsey.com`, in the tool's namespace. `inlinetools` has no CRD and serves no traffic: it exists only so the permission is separable from `tools`, and holding `tools/create` never implies the ability to store executable code.

The install ships an unbound `inline-tool-author-role` ClusterRole. Granting it is an explicit, per-namespace administrator action:

```bash
kubectl create rolebinding inline-authors \
  --clusterrole=inline-tool-author-role \
  --user=alice@example.com \
  --namespace=default
```

The check is fail-closed in every direction: feature disabled, no authenticated identity, no authorization backend, no namespace, review error, or review timeout (10s) all deny the write. Metadata-only updates — labels and annotations with an unchanged spec — do not re-check the permission.

Writes through ark-api must carry an end-user identity: inline authoring requires impersonation to be enabled and a username present, so inline source is never persisted under ark-api's service account.

### Authorship annotations

On each admitted inline spec write, admission stamps:

| Annotation | Value |
| --- | --- |
| `ark.mckinsey.com/inline-authored-by` | Authenticated username of the author. |
| `ark.mckinsey.com/inline-authored-at` | RFC 3339 UTC timestamp of the write. |

Both are overwritten by admission, so a requester cannot set them, and both survive metadata-only updates. They are the durable authorship record independent of cluster audit logging.

## Referencing tools from an agent

Agents reference tools in `spec.tools`, each with a `type` matching the Tool's type and the Tool's `name`:

```yaml
tools:
  - type: http
    name: get-coordinates
  - type: mcp
    name: filesys-server-read-file
  - type: agent
    name: call-research-agent
  - type: team
    name: research-team-tool
  - type: builtin
    name: terminate
```

> `type: custom` is deprecated. Use the explicit tool type instead — the mutating webhook stamps a migration warning on agents that still use it.

### Partial tools

`partial` pre-configures some of a tool's parameters at the agent level and hides them from the LLM, exposing only the rest. `partial.name` is the real Tool CRD; the outer `name`/`description` are what the agent sees.

```yaml
tools:
  - type: http
    name: weather-forecast            # name exposed to the agent
    description: "Get the latest weather forecast"
    partial:
      name: weather-api               # the real Tool CRD (type: http)
      parameters:
        - name: city
          value: "{{ .Query.city }}"  # sourced from a query parameter
        - name: units
          value: "metric"             # pinned static value
```

## Validation

Enforced by `ark/internal/validation/tool.go`:

- `inputSchema`, if set, must be valid JSON Schema.
- `type: http` requires `http.url`; the method (if set) must be a valid HTTP verb.
- `type: mcp` requires `mcp.mcpServerRef` and `mcp.toolName`.
- `type: agent` requires `agent.name`; `type: team` requires `team.name`.
- `type: builtin` requires the resource name to be a supported built-in (`terminate`, `noop`).
- `type: inline` requires a non-whitespace `inline.source` of at most 65536 UTF-8 bytes and an `inline.language` of `bash`, `python`, `node`, or `ts`; its `inputSchema`, if set, must describe a JSON object. Changing a tool's type to or from `inline` is rejected.
