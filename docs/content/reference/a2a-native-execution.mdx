## 2026-02 Payload-Only Contract Update

As of the payload-only cutover, Ark treats A2A `parts` as the only transport for invocation/lifecycle/result semantics.

- Delegated invocation semantics use `data` parts with schema `https://ark.mckinsey.com/payloads/delegated-invocation/v1`.
- Tool lifecycle semantics use `data` parts with schema `https://ark.mckinsey.com/payloads/step-event/v1`.
- Tool outcomes use `data` parts with schema `https://ark.mckinsey.com/payloads/tool-result/v1`.
- Extension metadata is still valid, but only under URI-attributed keys declared in `message.extensions` and negotiated via `A2A-Extensions`.
- Non-extension metadata keys are preserved for passthrough between A2A agents.

## Executive Summary

Ark uses **A2A as its canonical internal transport format**, with protocol conversion happening at system edges.

### Background

Ark previously used **OpenAI Chat Completions API format** (`ChatCompletionMessageParamUnion`) as its internal message representation. This created friction when:
- Integrating A2A-native agents (required conversion on every message)
- Supporting non-OpenAI models (forced OpenAI-shaped abstractions)
- Delegating between agents (lost semantic richness)

### Proposed Architecture

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                              EXTERNAL EDGES                                  │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐    │
│  │   OpenAI     │  │   Response   │  │   External   │  │   Claude/    │    │
│  │   Chat API   │  │     API      │  │   A2A Agents │  │   Gemini     │    │
│  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘  └──────┬───────┘    │
│         │                 │                 │                 │             │
│         ▼                 ▼                 ▼                 ▼             │
│  ┌──────────────────────────────────────────────────────────────────────┐  │
│  │                      EDGE ADAPTERS (Conversion Layer)                 │  │
│  │   ChatCompletions ↔ A2A    ResponseAPI ↔ A2A    Passthrough          │  │
│  └──────────────────────────────────────────────────────────────────────┘  │
│                                    │                                        │
```

**Key Principle**: A2A inside, convert at edges. This isolates format-specific logic to boundary adapters while the core operates on a single, rich message format.

## Part 1: Why A2A as Internal Transport?

### Current Pain Points

Ark's internal use of OpenAI Chat Completions format creates measurable friction:

| Problem | Evidence | Impact |
|---------|----------|--------|
| **Conversion overhead** | `message_conversion.go`: 200+ lines of `A2AToOpenAI`/`OpenAIToA2A` | Every A2A agent interaction requires bidirectional conversion |
| **Lossy transformation** | `extractTextFromParts()` flattens rich content to string | Multi-part messages (files, structured data) lose fidelity |
| **Metadata via conventions** | Legacy `ark.mckinsey.com/*` keys | Replaced by typed payload parts with explicit schema URIs |
| **String-only delegation** | `agent_tools.go:292`: `input parameter is required` | Agent-as-tool limited to single string input |

### Why Not Just Add Response API Support?

Issue #965 proposes adding OpenAI Response API support. This is valuable for OpenAI-native workloads, but it doesn't solve the internal transport problem:

| Aspect | Chat Completions | Response API | A2A |
|--------|-----------------|--------------|-----|
| **Current Ark status** | Edge adapter | Not implemented | Default internal transport |
| **Message format** | `{role, content}` | `{role, content[]}` | `{role, parts[]}` |
| **Multi-modal** | Via content array | Native | Native |
| **Agent discovery** | None | None | AgentCard spec |
| **Task lifecycle** | Implicit | Session-based | Explicit states |
| **Cross-platform** | OpenAI-specific | OpenAI-specific | Provider-agnostic |

**Observation**: Both Chat Completions and Response API are OpenAI-specific formats. Using either as internal transport couples Ark to OpenAI's abstractions.

**Recommendation**: Support Response API at the edge (alongside Chat Completions), but use A2A internally. This provides:
- OpenAI compatibility via edge adapters
- Provider-agnostic internal execution
- Native support for A2A agents without conversion

### A2A Advantages for Internal Transport

| Capability | Benefit for Ark |
|------------|----------------|
| **Rich message parts** | Files, structured data, text flow natively—no base64 encoding in message bodies |
| **Native tool representation** | Tool calls and results are first-class, not metadata conventions |
| **Explicit task states** | `submitted → working → completed` maps directly to Query CRD phases |
| **Delegation metadata** | Agent-as-tool can pass structured context, not just string input |
| **Provider-agnostic** | Same internal format regardless of model backend (OpenAI, Claude, Gemini, etc.) |

### A2A Limitations (Honest Assessment)

| Limitation | Mitigation |
|------------|------------|
| **Emerging standard** | Edge adapters maintain full Chat Completions compatibility |
| **Smaller ecosystem** | Edge adapters maintain Chat Completions compatibility |
| **No built-in features** | Response API's code interpreter/file search require explicit tool implementations |
| **Learning curve** | Internal change; external APIs remain familiar |

## Part 2: Edge Adapter Architecture

### Adapter Types

```go
// Edge adapters convert between A2A and external formats
type EdgeAdapter interface {
    // Inbound: External format → A2A
    ToA2A(input ExternalMessage) (protocol.Message, error)
    // Outbound: A2A → External format
    FromA2A(msg protocol.Message) (ExternalMessage, error)
}
```

### Supported Edges

| Edge | Adapter | Direction | Status |
|------|---------|-----------|--------|
| **OpenAI Chat Completions** | `ChatCompletionsAdapter` | Bidirectional | Implemented (edge-only) |
| **OpenAI Response API** | `ResponseAPIAdapter` | Bidirectional | Planned (#965) |
| **External A2A Agents** | Passthrough | Native | Implemented |
| **A2A Gateway (ark-api)** | Passthrough | Native | Implemented |

### Conversion Points

**Current (problematic)**:
```
External → OpenAI format → Internal processing → OpenAI format → External
                ↑                                      ↑
           Conversion here                    And conversion here
           (for A2A agents)                   (back to A2A)
```

**Proposed**:
```
External → Edge Adapter → A2A internal → Edge Adapter → External
              ↑                               ↑
         Convert once                    Convert once
         (at boundary)                   (at boundary)
```

### Example: Agent-as-Tool with Structured Delegation

**Current (Chat Completions internal)**:
```go
// agent_tools.go - input is always a string
input, exists := arguments["input"]  // string only
if !exists {
    return ToolResult{Error: "input parameter is required"}
}
```

**Proposed (A2A internal)**:
```go
// Delegation message carries structured context in typed data parts
delegationMsg := protocol.Message{
    Role: protocol.MessageRoleUser,
    Parts: []protocol.Part{
        protocol.NewTextPart(userInput),
        &protocol.DataPart{
            Kind: protocol.KindData,
            Data: map[string]any{
                "schema":     "https://ark.mckinsey.com/payloads/delegated-invocation/v1",
                "parameters": arguments,
            },
        },
    },
}
```

## Part 3: Technical Specification

### Default Behavior

Agent and team execution use A2A internal transport unconditionally. No annotation or configuration is required.

### Internal Execution Flow

1. **Query Input**: Controller resolves compat query input (`GetQueryInputMessages`); agent/team entrypoints convert it to `[]protocol.Message` at the execution boundary
2. **Agent Execution**: Routes through capability resolution:
   - Reserved "a2a" engine → `ExecuteNative` (direct A2A task execution)
   - Named external engines → `ExecutionEngineA2AClient.ExecuteA2A` (A2A SendMessage protocol)
   - Model-backed agents (no engine) → native local A2A loop (convert only at model boundary)
3. **Team Strategies**: `executeSequentialA2A`, `executeRoundRobinA2A`, etc.
4. **Memory**: Controller writes `AddA2AMessages` for native outputs (fallback `AddMessages` for compat-only payloads) and reads through `GetMessages` compatibility view
5. **Tool Delegation**: `ExecuteA2A` with structured metadata
6. **Response**: Controller projects native `ExecutionResult.A2AMessages` / `A2AResponse` to compat Query response payloads while preserving A2A metadata

### Model Boundary Conversion

Even with A2A internal, model calls require format conversion:

```
┌─────────────────────────────────────────────────────────────────┐
│                    ARK INTERNAL (A2A)                            │
│                                                                  │
│   protocol.Message ──┬──────────────────────────────────────────│
│                      │                                           │
│                      ▼                                           │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │              MODEL BOUNDARY ADAPTER                      │   │
│   │   A2A → ChatCompletions (for OpenAI/Azure/Bedrock)      │   │
│   │   A2A → Claude Messages (for Anthropic)                 │   │
│   │   A2A → Gemini Format (for Google)                      │   │
│   └─────────────────────────────────────────────────────────┘   │
│                      │                                           │
│                      ▼                                           │
│   Model Provider API call                                        │
│                      │                                           │
│                      ▼                                           │
│   ┌─────────────────────────────────────────────────────────┐   │
│   │              RESPONSE ADAPTER                            │   │
│   │   ChatCompletion → A2A (extract content, tool calls)    │   │
│   └─────────────────────────────────────────────────────────┘   │
│                      │                                           │
│                      ▼                                           │
│   protocol.Message ◀─┘                                           │
└─────────────────────────────────────────────────────────────────┘
```

This conversion is unavoidable—models speak their native formats. The key improvement is that this conversion happens **only at model boundaries**, not throughout the internal execution flow.

### Execution Surface

| Surface | Behavior |
|---------|----------|
| Query input | `GetQueryInputMessages` (compat) converted to `[]protocol.Message` at agent/team boundary |
| Internal payload | `protocol.Message` end-to-end for agent/team execution |
| Memory writes | `AddA2AMessages` for native outputs (`AddMessages` fallback for compat-only paths) |
| Memory reads | `GetMessages` compatibility view (decodes both A2A and legacy OpenAI records) |
| Delegation | A2A message + typed data parts (legacy `input` string fallback supported) |
| Response | Compat response serialization from A2A outputs at controller boundary (A2A metadata preserved) |

The `ark-api` service exposes an A2A JSON-RPC gateway that:
- Discovers Ark agents and builds A2A AgentCards
- Routes incoming A2A requests to Kubernetes Query CRDs
- Propagates A2A execution mode to created Queries
- Persists per-agent task stores for lifecycle continuity

This enables external systems to invoke Ark agents using A2A without Ark-specific knowledge.

## Part 5: A2A Extensions

### History Propagation

**Purpose**: Conversation continuity across distributed agents without shared storage.

```go
// Extension: bounded history window
message.Extensions["history"] = HistoryExtension{
    Messages: recentMessages[:maxWindow],
    Truncated: len(fullHistory) > maxWindow,
}
```

**Principles**:
- Declared and negotiated via AgentCard capabilities
- Size-bounded to prevent payload bloat
- Non-authoritative (receivers may ignore)

### Identity & Permissions

**Purpose**: Portable authorization context for distributed agent graphs.

```go
// Extension: delegated permissions
message.Extensions["identity"] = IdentityExtension{
    Principal:   callerIdentity,
    Scopes:      allowedScopes,
    Delegation:  delegationChain,
    Signature:   jwtSignature,  // Verifiable
}
```

**Principles**:
- Least-privilege: deny by default
- Verifiable: signed assertions (JWT/JWS)
- Delegation-aware: audit trail

```
├─────────────────────────────────────────────────────────────┤
│              Layer 3: Agent Communication                    │
```

A2A defines **how agents communicate**. Aggregation defines **how queries are stored and processed**. Both are needed; neither replaces the other.

## Part 7: Compatibility

### Version Support Contract

Ark supports **A2A v0.3 wire interoperability** as the production baseline.

V1 RC work is **adapter-scoped**:

- Read both v0.3 and V1-compatible shapes where practical at protocol boundaries.
- Emit versioned payload shapes intentionally, not by implicit fallback.

### Memory Compatibility

`unmarshalMessageRobust()` reads both formats:
- Legacy: `{"role": "user", "content": "text"}`
- A2A: `{"role": "user", "parts": [{"type": "text", "text": "..."}]}`

Existing OpenAI-format memory remains readable. No migration is required for stored messages.

### Execution Engine Compatibility

All execution engines communicate via A2A SendMessage protocol. PR #1215 established this as the single engine contract — engines no longer declare a type field. The `ExecutionEngineA2AClient` handles all external engine communication.

### Chat Completions Compatibility

OpenAI Chat Completions format is maintained at edge boundaries:
- The controller can serialize responses in compat (OpenAI) format when needed
- Model provider adapters convert between A2A and provider-specific formats at the model boundary
- Legacy delegation input (`input` string) is still accepted with automatic conversion to A2A

### Adapter Boundary Contracts

| Boundary | Behavior |
| --- | --- |
| `message_conversion.go` / `message_conversion_multimodal.go` | Content-part-aware converters preserve text/image file parts across A2A and OpenAI compat messages |
| `openai_a2a_model_adapter.go` + `a2a_execution_local.go` | Model adapter converts between A2A and provider-specific formats at the model boundary |
| `execution_engine.go` | `ExecutionEngineA2AClient` uses A2A SendMessage protocol for all external engines |
| `provider_bedrock.go` | Bedrock path extracts array content parts (`text`, `image_url`) and projects to Bedrock content |
| `memory_http.go` | Native A2A flows use native message APIs; legacy OpenAI format remains readable |

Lossless rules for all adapters:

- Preserve part order for `parts[]` and content arrays.
- Preserve `messageId`, `taskId`, and `contextId` when present.
- Preserve task lifecycle state transitions in streaming mode.
- Preserve delegated tool extension metadata (`https://ark.mckinsey.com/extensions/delegated-tool/v1`).

## Part 8: Native Execution Engine Architecture

### Old Path vs New Path

The native A2A local execution loop previously relied on OpenAI Chat Completions types as its internal conversation representation. Every loop iteration converted A2A `protocol.Message` to `openai.ChatCompletionMessageParamUnion`, called the model, then converted the response back to A2A format.

```
Old native loop:
  protocol.Message → convertA2AMessagesToCompat() → []openai.ChatCompletionMessageParamUnion
                   → Model.ChatCompletion()       → openai.ChatCompletion
                   → processAssistantMessage()    → openai.ChatCompletionMessageParamUnion
                   → OpenAIToA2AMessage()          → protocol.Message
```

The new architecture introduces a **dedicated A2A local engine** (`A2ALocalEngine`) that operates entirely on `protocol.Message` and provider-neutral types. OpenAI-specific conversion is isolated inside a **model adapter** boundary.

```
New native loop:
  protocol.Message → A2ALocalEngine.Execute()
                  → A2AModelProvider.A2ATurn()  ← provider-neutral interface
                   → A2ATurnResult{Message, ToolCalls}
                  → executeA2AToolCalls() using A2AToolCall (no OpenAI types)
                  → []A2AToolOutcome (structured outcomes, no synthetic tool message)
```

### Boundary Contracts

| Type | Purpose | Location |
|------|---------|----------|
| `A2AModelProvider` | Provider-neutral model interface accepting `[]protocol.Message` | `a2a_model_provider.go` |
| `A2ATurnResult` | Model response: `protocol.Message` + `[]A2AToolCall` | `a2a_model_provider.go` |
| `A2AToolCall` | Tool call with `ID`, `Name`, `Arguments` (no OpenAI types) | `a2a_model_provider.go` |
| `A2AToolOutcome` | Structured tool outcome for next model turn (`toolCallId`, `taskId`, `contextId`, content/error) | `a2a_model_provider.go` |
| `A2AToolDefinition` | Tool schema with `Name`, `Description`, `Parameters` | `a2a_model_provider.go` |
| `A2ALocalEngine` | Turn loop operating on A2A types only | `a2a_local_engine.go` |
| `OpenAIA2AModelAdapter` | Adapter wrapping `ChatCompletionProvider` behind `A2AModelProvider` | `openai_a2a_model_adapter.go` |
| `ErrA2AModelProviderNotSupported` | Hard-fail sentinel when no A2A adapter is available | `a2a_model_provider.go` |

### Execution Engine Strategy

The engine boundary is designed for pluggable model backends:

```
A2ALocalEngine
  ├── OpenAIA2AModelAdapter   (wraps OpenAI/Azure/Bedrock ChatCompletion providers)
  ├── [future] claudeAdapter  (wraps Anthropic Messages API)
  ├── [future] geminiAdapter  (wraps Google GenerateContent)
  └── nil → ErrA2AModelProviderNotSupported (hard-fail, no silent fallback)
```

To add a new backend, implement `A2AModelProvider` and wire it in `executeLocallyA2ANative()`. The engine loop, tool execution, streaming, and telemetry remain unchanged.

### Hard-Fail Behavior

If a provider does not have an A2A adapter, the engine returns `ErrA2AModelProviderNotSupported` immediately. There is no silent fallback from native mode to compat mode. This is enforced at the `A2ALocalEngine.Execute()` entry point.

### Task-First Delegated Tool Semantics

Native delegated execution is task-first and event-first:

- Delegated tool activity is streamed upstream as native A2A events (`TaskStatusUpdateEvent`, `TaskArtifactUpdateEvent`, task-scoped messages).
- Correlation/lifecycle data is attached as typed `step-event` data parts.
- The native loop does not inject synthetic tool-result messages into the A2A message history.
- Tool outcomes are passed to the next provider turn through `[]A2AToolOutcome`.
- OpenAI provider deltas are adapter-internal and are not forwarded on the native delegated event stream.

This keeps the internal native path aligned with A2A task lifecycle semantics while retaining explicit adapter behavior for providers that need OpenAI tool messages.

## Conclusion

Ark uses A2A as its internal transport:

1. **A2A as internal transport**: Rich, provider-agnostic message format
2. **Edge adapters for compatibility**: Chat Completions, Response API, external A2A
3. **Convert at boundaries, not throughout**: Single conversion point per external interaction

This architecture enables:
- External agents to integrate via A2A protocol
- Internal agents to leverage A2A's rich semantics
- Existing OpenAI workloads to continue unchanged (via edge adapters)
- Future Response API support as another edge adapter

The runtime follows a single A2A-first execution path for all agent and team targets.
