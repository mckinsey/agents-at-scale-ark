# Deploying Ark

Deploy Ark locally using the CLI, Helm, or to remote clusters with registry-based deployment.

## Required resources

Running Ark requires at least 2 vCPU and 4 GiB of RAM. Further resource consumption depends on individual workflows and load.

## Install with the CLI

For the standard CLI install, follow the [Quickstart](/quickstart), which is kept current and tested. This page covers: Helm and remote-cluster deployment, storage backends, private registries, CI/CD RBAC, and multi-tenant operation.

### Storage backend

`ark install` reads the storage backend from `.arkrc.yaml`. The default is `etcd`, which stores resources as CRDs. The PostgreSQL path uses an aggregated API server backed by Postgres and is suited for larger fleets, oversize resources, or shared-DB strategies.

To use PostgreSQL, add a `storage` block to `.arkrc.yaml`:

```yaml
storage:
  backend: postgresql
  postgresql:
    host: db.example.com
    user: ark
    passwordSecretName: ark-db-password
```

Then run `ark install` as usual. The `--backend` CLI flag overrides the config value (e.g., `--backend etcd` for a temporary switch). See [PostgreSQL Storage Backend](/operations-guide/postgres-storage-backend) for the full setup, database requirements, and operational notes.

## Local Development

To run in local development mode with live-reload, install [Devspace](https://devspace.sh), clone and run:

```bash
# Clone the repo, move to the project.
git clone https://github.com/mckinsey/agents-at-scale-ark.git
cd agents-at-scale-ark

# Run with live-reload for local development.
devspace dev
```

More details are in the [Local Development](../../developer-guide/local-development) developer guide. 

## Deploying via Helm

Ark can be deployed using the Helm charts that are attached to all [releases](https://github.com/mckinsey/agents-at-scale-ark/releases/) and deployed to the [charts packages](https://github.com/orgs/mckinsey/packages?repo_name=agents-at-scale-ark). By default the chart uses the latest images available on the release. This process, including the deployment of prerequisites can also be run via the `ark install` command.

Install prerequisites on your remote cluster:

```bash
# Install cert-manager
helm repo add jetstack https://charts.jetstack.io --force-update  
helm repo update
helm upgrade --install cert-manager jetstack/cert-manager \
  --namespace cert-manager \
  --create-namespace \
  --set crds.enabled=true

# Install Gateway API CRDs
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.3.0/standard-install.yaml
```

Deploy the Ark controller:

```bash
helm upgrade --install \
  ark-controller oci://ghcr.io/mckinsey/agents-at-scale-ark/charts/ark-controller \
  --namespace ark-system \
  --create-namespace \
  --set rbac.enable=true
```

In many cases, you will want to install the `ark-api` and `ark-dashboard` services as well. When running on a local cluster you may also want to install the `localhost-gateway`:

```bash
helm upgrade --install ark-api oci://ghcr.io/mckinsey/agents-at-scale-ark/charts/ark-api
helm upgrade --install ark-dashboard oci://ghcr.io/mckinsey/agents-at-scale-ark/charts/ark-dashboard
helm upgrade --install localhost-gateway oci://ghcr.io/mckinsey/agents-at-scale-ark/charts/localhost-gateway
```

The `fark` (Fast Agentic Runtime Kit) CLI can be built from source:

```bash
cd tools/fark
go build -o fark ./cmd/fark
cp fark /usr/local/bin
fark
```

Or installed via the [GitHub Releases](https://github.com/mckinsey/agents-at-scale-ark/releases)

### Deploying from a Private Registry

The chart can be configured to install containers hosted in any registry:

```bash
helm upgrade --install \
  ark-controller oci://ghcr.io/mckinsey/agents-at-scale-ark/charts/ark-controller \
  --version 0.1.31 \
  --namespace ark-system \
  --create-namespace \
  --set controllerManager.container.image.repository=your-registry.com/ark-controller \
  --set controllerManager.container.image.tag=0.1.31 \
  --set containerRegistry.enabled=true \
  --set containerRegistry.server=your-registry.com \
  --set containerRegistry.username=your_username \
  --set containerRegistry.password=your_token \
  --set rbac.enable=true

helm upgrade --install \
  ark-completions oci://ghcr.io/mckinsey/agents-at-scale-ark/charts/ark-completions \
  --version 0.1.31 \
  --namespace ark-system \
  --set image.repository=your-registry.com/ark-completions \
  --set image.tag=0.1.31
```

If you need to transfer containers between registries, use the transfer script:

```bash
# Transfer from source registry to your target registry
export SOURCE_DOCKER_REGISTRY=source-registry.com  
export TARGET_DOCKER_REGISTRY=your-registry.com
export TARGET_DOCKER_USERNAME=your_username
export TARGET_DOCKER_TOKEN=your_token
export VERSION=0.1.31
./scripts/deploy/transfer-ark-containers.sh
```

## Checking Ark Version and Status

Once deployed, you can check the running version:

```bash
# Via Helm
helm list -n ark-system

# Via deployment labels  
kubectl get deployment ark-controller -n ark-system \
  -o jsonpath='{.metadata.labels.app\.kubernetes\.io/version}'
```

The Ark CLI can be used to show the status of all running Ark services and their versions, with the `ark status` command.

```bash
# Check overall system status
ark status
```

## Cluster Preparation for CI/CD Deployments

Before using GitHub Actions to deploy Ark to a cluster, platform administrators need to set up the required RBAC permissions.

Ark includes a standard deployer role in [`ark/config/rbac/ark-deployer-role.yaml`](https://github.com/mckinsey/agents-at-scale-ark/blob/main/ark/config/rbac/ark-deployer-role.yaml) that defines the minimum permissions required for deployments. This role allows creating namespaces, deploying services, installing CRDs, and configuring webhooks.

### Setup Process

Apply the standard Ark deployer role and then bind to the repository - this will ensure that your GitHub Actions will be able to deploy Ark. In many cases you will have to specify the specific runner via `runs_on` but this will depend on your organization's OIDC configuration:

```bash
# Create the ark deployer role, which has the necessary permissions to
# deploy Ark.
kubectl apply -f ark/config/rbac/ark-deployer-role.yaml

# Add the GitHub repository to the role. This allows GitHub workflows to
# deploy Ark to any cluster they have OIDC access to.
./scripts/deploy/bind-deployer-role.sh "mckinsey/agents-at-scale-ark"
```

This creates a ClusterRoleBinding that connects your GitHub repository identity (via OIDC) to the deployment permissions.

## The Ark Controller

By default, the `ark-controller` is deployed into the `ark-system` namespace. When the controller executes a query, it can optionally impersonate the service account specified in the `query.serviceAccount` field. Impersonation is enabled by default and can be configured via the `ark-controller` chart values:

```yaml
# values.yaml for ark-controller
rbac:
  enable: true
  impersonation:
    # Allow impersonation when requested by queries.
    enabled: true
```

When enabled (default), the controller can impersonate any service account specified in queries. When disabled, queries can only run with the controller's own identity. If no `serviceAccount` is specified for a query, no impersonation will occur and the `ark-controller` will execute the query using its own service account.

### Inline Tool Authoring

Inline tools store executable source in the `Tool` resource. Authoring is disabled by default and fails closed:

```yaml
# values.yaml for ark-controller (and for ark-apiserver on the postgresql backend)
inlineTools:
  enabled: false
```

Enabling it renders `ARK_INLINE_TOOLS_ENABLED=true` on the controller and API server. Both write paths check the flag separately, so on the PostgreSQL backend set it in both charts. On the `etcd` backend it requires `webhook.enable=true` — the chart fails to render otherwise, since the inline admission webhook is what enforces the author check.

Enabling the flag grants nobody anything. Every inline create and spec update is checked by `SubjectAccessReview` for `use` on `inlinetools.ark.mckinsey.com` in the tool's namespace, and the shipped `inline-tool-author-role` ClusterRole is unbound. Bind it per namespace, deliberately:

```bash
kubectl create rolebinding inline-authors \
  --clusterrole=inline-tool-author-role \
  --user=alice@example.com \
  --namespace=tenant-1
```

Writes through ark-api additionally require impersonation, so inline source is never stored under ark-api's service account. Ark stamps `ark.mckinsey.com/inline-authored-by` and `ark.mckinsey.com/inline-authored-at` on each admitted write as a durable authorship record independent of audit logging. See [Reference → Tools → Inline tools](/reference/resources/tools#inline-tools).

#### Install the singleton activator

Install the runtime independently of the authoring/invocation flag. In the controller chart, set:

```yaml
controllerManager:
  watchNamespaces: [ark-system, tenant-1]
inlineTools:
  enabled: false
  activator:
    enabled: true
```

Create the watched namespaces first and include the Helm release namespace. The chart rejects an empty scope, disabled RBAC, or invocation enabled without the activator installed; it never grants the activator a cluster-wide binding. On upgrade, retain these values and merge new chart defaults, for example with Helm's `--reset-then-reuse-values`.

The activator reuses the controller image with `--role=inline-activator`, a dedicated ServiceAccount, and exactly one replica regardless of controller replica count. Its `Recreate` strategy prevents overlapping scaling authorities during rollout; shutdown waits up to 90 seconds for accepted HTTP calls, within a 95-second pod termination grace period. Do not scale it above one replica or force-delete its pod: Recreate orders Deployment rollouts, not manual pod replacement or node-partition recovery. A rollout can briefly interrupt availability; uncertain calls must not be replayed.

A dedicated ClusterRole is bound only through a RoleBinding in each watched namespace. It grants Tool `get`, Deployment `get/list`, Service/Pod/ReplicaSet `get`, EndpointSlice `list`, and Deployment `scale` `update`; it grants no Secret access or Tool writes. RBAC cannot filter by labels or owner references: these credentials can scale **any** Deployment in a bound namespace. The activator's UID, ownership and revision checks restrict normal operation to owned runners; a compromised activator remains privileged across those namespaces.

The Service is internal-only. A mandatory ingress NetworkPolicy admits TCP 8080 from the release namespace's `control-plane: ark-controller` and `app: ark-completions` pods by default. To allow other executor workloads, replace `inlineTools.activator.allowedCallers` with entries containing `namespace` and non-empty `podLabels`; an empty namespace means the release namespace. Replacing that list replaces the defaults, so retain every required caller. Administrators must prevent additive policies from widening this boundary and protect these labels; it is not per-user authentication.

The chart rejects installing the activator with `networkPolicy.enable=true`, even with invocation disabled: its `ark-system-baseline` policy allows every same-namespace pod to reach the activator. Before disabling that option, replace the baseline, webhook, metrics and ingress protections it installs with appropriately scoped policies that do not widen activator ingress. The guard catches this known chart conflict only, not other administrator policies, and does not verify CNI enforcement.

#### Runner infrastructure

With the feature enabled, the controller provisions one ConfigMap, ServiceAccount, Service, NetworkPolicy and Deployment per inline tool, in the tool's namespace. The Deployment starts at zero replicas, so an authored-but-unused tool costs no pods. Runner images are fixed per language and not overridable per tool:

```yaml
controllerManager:
  watchNamespaces: [ark-system, tenant-1]
inlineTools:
  enabled: true
  activator:
    enabled: true
  runner:
    image:
      repository: ghcr.io/mckinsey/agents-at-scale-ark/ark-inline-runner
      tag: ""   # defaults to the chart's appVersion
```

The controller appends `-bash`, `-python` or `-node` to that repository; the node image also runs the `ts` language.

Two deployment prerequisites are not things Ark can verify at runtime:

- **The CNI must enforce NetworkPolicy.** Ark creates a policy that denies all runner egress and admits only the activator, but that policy is inert on a CNI that does not enforce policies (k3s with flannel, for example). Ark sends no probe traffic to test it and does not gate execution on it. Policies are also additive: a namespace-wide allow-all policy — including the optional `ark-tenant` one, whose empty pod selector allows all egress — defeats it.
- **Per-pod PID limits are the cluster's responsibility.** A script can exhaust node PIDs before its 30-second timeout expires. CPU and memory limits do not contain that. Configure a finite per-pod limit through kubelet `podPidsLimit` or your provider's equivalent, size it for processes and threads, and verify it outside production. Ark does not set, require, or check it.

#### Runner network boundary

Runner policies deny all egress, including DNS, and allow backend ingress only from activator pods in the configured activator namespace on TCP 8080. Policies are additive: the optional `ark-tenant` allow-all policy defeats both restrictions. An administrator must narrow overlapping policies to exclude runner pods or grant no access beyond that boundary; Ark must not rewrite tenant policies.

The policy-conflict decision checks pod selectors, not a policy's metadata labels. Ingress peers must constrain both the activator's pod identity and namespace; a pod selector alone means the policy's own namespace. Matching the activator's current labels is not enough: a broad selector could also admit other workloads. Identity constraints use `matchLabels` or a single-value `In` expression; additional constraints may narrow access. Selectors whose containment cannot be established conservatively count as conflicts, even if they currently select no workloads.

The controller checks policies against both the runner template and live runner pod labels. A conflict clears `status.resolvedAddress` and reports `Available=False`, reason `ConflictingNetworkPolicy`, with the policy name and an instruction to narrow it. Narrowing or deleting the policy restores availability once other runtime prerequisites are met. Policy and pod-label changes trigger re-evaluation; a 30-second API-only refresh also recovers missed events. If required policy or pod reads fail, the tool remains Pending with `ProvisioningFailed`. Removing identifying labels from a runner pod also blocks availability until an administrator restores them.

The controller needs read-only access to Pods and ReplicaSets to follow runner ownership even after labels change. It changes only the policy it owns, never a tenant policy. **Rollout status:** executor integration remains incomplete; inline tools are disabled by default.

An enforcing CNI is still required. On a non-enforcing CNI, outbound script connections and direct runner access may succeed despite the policy. Standard NetworkPolicy also has node-local traffic exceptions: administrators must protect node and metadata-service access and control who can change workload labels or policies. These restrictions are not per-user authentication, and Ark sends no traffic probes or synthetic control connections to verify them.

#### Metadata-only discovery

The activator's stateless MCP handler serves initialization, notifications, ping, and `tools/list` from the current Tool metadata. Each namespace/name/UID route advertises only that Tool's name, description, input schema and annotations; an omitted schema becomes `{"type":"object"}`. Source is never included. Discovery does not read runner resources, invoke a call, or refresh an idle timer.

Routes outside the explicitly watched namespaces, deleted/recreated Tools, and unknown names are rejected. API read failures and malformed schemas fail closed. Only `tools/call` reaches the separate invocation handler.

Stateless `tools/call` work is tied to its HTTP request lifetime. Disconnecting cancels the invocation context and terminates a running script's process group rather than waiting for the execution limit. Cancellation cannot roll back effects already dispatched; treat a lost response as uncertain execution.

#### Activation identity checks

The activation decision requires an enabled feature, a matching Tool name and UID, and `Available=True` for the current generation with the canonical published activator address. It rejects missing, deleting, cross-namespace, or unowned runner resources and stale source/language identity. The backend address is derived from the controller's shared child names and private Service, never a caller-supplied URL.

An idle Deployment may pass this decision: it authorizes a target, not execution. The activator validates bounded JSON-object arguments before scaling, coalesces cold starts for the selected Tool, and waits for an observed Deployment rollout plus current, owned Pod endpoints. EndpointSlice addresses, Pod UID/source/language, and ReplicaSet ownership must match; stale or unverifiable endpoints block connection. It rechecks identity and readiness after the MCP handshake and rejects backend redirects.

#### Activation and idle lifetime

Activation, including the handshake, has a 60-second budget. Execution then has a separate 30-second budget; caller cancellation or an earlier caller deadline bounds both. Pending and active calls prevent idle scale-down. With neither remaining, the activator scales to zero after 60 seconds since the last completed call; discovery never refreshes that clock.

On restart, existing warm owned runners receive a fresh 60-second grace period before idle cleanup. Scale writes use the scale subresource with optimistic concurrency, and failed reads or changed ownership prevent the write. The controller alone performs bounded drain while the feature is disabled. Backend calls are sent once: uncertain responses are not replayed.

**Rollout status:** executor integration remains pending. Keep inline tools disabled in production until that integration is available.

#### Disabling, deleting and downgrading

Order matters, because a runner Deployment outlives the flag that created it:

1. **Disable authoring and invocation:** set `inlineTools.enabled=false`, retain `inlineTools.activator.enabled=true`, and upgrade. The controller withdraws each tool's endpoint immediately, then scales any running runner to zero after a bounded drain so work already in flight is not cut off mid-call. Reconciliation deliberately keeps running while disabled — it is what scales those pods down — and the controller keeps its workload permissions for the same reason.
2. **Delete the inline tools:** `kubectl delete tool <name>`. The controller removes the owned children itself rather than relying on garbage collection, so this behaves the same on the etcd and PostgreSQL backends. Verify before continuing:

   ```bash
   kubectl get tools -A -o jsonpath='{range .items[?(@.spec.type=="inline")]}{.metadata.namespace}/{.metadata.name}{"\n"}{end}'
   kubectl get deploy,svc,cm,netpol -A -l app.kubernetes.io/name=ark-inline-runner
   ```

3. **Only then replace or downgrade the operator.** Reverting to a release that does not understand `type: inline` does not stop surviving runner pods or make them inert — nothing would be left to reconcile or delete them. Set `inlineTools.activator.enabled=false` to remove the runtime only after no inline tools or owned runner resources remain.

### Setting Up Tenant Namespaces

The `ark-tenant` Helm chart provisions namespaces for Ark workloads:

```bash
helm install ark-tenant oci://ghcr.io/mckinsey/agents-at-scale-ark/charts/ark-tenant \
  -n tenant-1 \
  --create-namespace \
  --set serviceAccount.name=ark-tenant \
  --set memory.requireBroker=false
```

The chart refuses a fresh install into a namespace with no `ark-broker` Service, because a tenant without a broker loses conversation history. This command provisions RBAC only, so it passes `memory.requireBroker=false` to skip that check. Drop the flag once you install `ark-broker` into the same namespace — see [Tenant and Namespace Management](/operations-guide/tenant-namespace-management).

This creates:
- The namespace (if it doesn't exist)
- The service account
- An `ark-tenant-role` with Ark and Kubernetes permissions
- A RoleBinding linking the service account to the role
- Builtin tools (`terminate`, `noop`) for agent workflows

Resource quotas and network policies are also available, documented in the chart. Queries then run under this service account via their `query.serviceAccount` field (subject to the impersonation setting above); omit it to use the controller's own identity.

The [Tenant and Namespace Management](/operations-guide/tenant-namespace-management) guide is the canonical reference for multi-tenancy — CLI-based setup, cross-tenant access via RBAC, broker storage isolation, and the development workflow.
