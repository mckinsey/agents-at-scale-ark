# Tenant and Namespace Management

Each Ark tenant is a Kubernetes namespace. By default, tenants are fully isolated — a tenant's service account can only access resources in its own namespace.

The Ark dashboard and API layer accept a `?namespace=` query parameter on all resource endpoints. This allows a single dashboard instance to view and administer resources across multiple tenants, but only if the tenant's RBAC permits cross-namespace access.

## Cross-Namespace Access

By default, a tenant cannot see or modify resources in another namespace. A cluster administrator must explicitly grant access using standard Kubernetes RBAC.

For example, to allow `ark-api-sa` in namespace `tenant-a` to read Ark resources in `tenant-b`:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: tenant-a-access
  namespace: tenant-b
subjects:
  - kind: ServiceAccount
    name: ark-api-sa
    namespace: tenant-a
roleRef:
  kind: ClusterRole
  name: ark-tenant-role
  apiGroup: rbac.authorization.k8s.io
```

This uses the existing `ark-tenant-role` (created by the tenant Helm chart) and binds it in the target namespace. No ClusterRole creation is needed.

## Namespace Discovery

To allow a tenant to list available namespaces (e.g. for namespace discovery in the API), a cluster administrator can grant namespace read access:

```yaml
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRole
metadata:
  name: ark-namespace-reader
rules:
  - apiGroups: [""]
    resources: ["namespaces"]
    verbs: ["get", "list"]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: ClusterRoleBinding
metadata:
  name: ark-namespace-reader-binding
subjects:
  - kind: ServiceAccount
    name: ark-api-sa
    namespace: tenant-a
roleRef:
  kind: ClusterRole
  name: ark-namespace-reader
  apiGroup: rbac.authorization.k8s.io
```

Without this, the `GET /api/v1/namespaces` endpoint returns an error. The dashboard and API still function normally for the tenant's own namespace.
