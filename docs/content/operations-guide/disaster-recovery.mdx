# Disaster Recovery

Ark runs on Kubernetes and stores its state in three places: custom resources in etcd, Kubernetes Secrets, and optionally an external database for conversation memory. All runtime services (operator, API, dashboard, broker) are stateless and can be redeployed from their Helm charts without data loss.

This guide outlines what needs to be protected and the general approach to recovery.

## What to back up

- **Ark custom resources** — All resources under the `ark.mckinsey.com` API group. These define your agents, teams, tools, models, and other platform configuration.
- **Kubernetes Secrets** — API keys, model credentials, and OIDC client secrets referenced by Ark resources.
- **RBAC bindings** — Any RoleBindings or ClusterRoleBindings that grant users access to Ark resources (relevant if you use [user impersonation](/developer-guide/authentication#user-impersonation)).
- **Helm values** — The configuration used to deploy Ark and its dependencies. Store these in version control.
- **Memory backend** — If you use an external database for conversation memory, back it up using your database provider's tooling. Ark does not manage the memory backend lifecycle.

## Recovery approach

### 1. Redeploy the operator

Install the Ark Helm chart with your stored values. This re-creates the CRDs, controller, webhooks, and supporting services. Wait for the operator to become ready before restoring data.

### 2. Restore custom resources

Apply your backed-up Ark resources. Restore dependencies before dependents — standalone resources (models, tools, memory backends) first, then resources that reference them (agents), then resources that reference those (teams).

### 3. Restore Secrets and RBAC

Re-apply Kubernetes Secrets and any RBAC bindings to their original namespaces.

### 4. Redeploy supporting services

Reinstall the API, dashboard, broker, and any marketplace components (executors, MCP servers). These are stateless and reconnect to the operator on startup.

### 5. Restore the memory backend

If applicable, restore your external conversation memory database independently.

### 6. Verify

Confirm the operator is reconciling resources, supporting services are healthy, and a test query executes successfully.

## Partial failures

- **Operator pod crash** — Kubernetes restarts it automatically. State lives in etcd, so no data is lost.
- **Stateless services down** (API, dashboard, broker) — Redeploy from Helm.
- **Single namespace lost** — Restore only that namespace's resources and Secrets. Other namespaces are unaffected.
- **Memory backend lost** — Agents continue to function but lose conversation history. Restore the database independently.

## Recommendations

- **Automate backups** — Tools like [Velero](https://velero.io/) can schedule regular backups of Kubernetes resources and volumes. All Ark resources share the `ark.mckinsey.com` API group, making them easy to filter.
- **Version-control your Helm values** — Ensures you can redeploy without guessing configuration.
- **Test restores regularly** — Restore to a staging cluster periodically to verify backups are complete.

For general Kubernetes backup and restore patterns, see the [Kubernetes documentation](https://kubernetes.io/docs/concepts/cluster-administration/).
