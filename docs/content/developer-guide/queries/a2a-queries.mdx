# A2A Queries

ARK translates Query resources into A2A protocol messages when targeting agents hosted on A2A servers.

When a Query targets an A2A-hosted agent, ARK automatically creates an [A2ATask](/reference/resources/a2atask) resource to track the A2A protocol interaction. For message-based queries that return immediately, the A2ATask completes synchronously with phase `completed`. For long-running tasks, the A2ATask tracks execution progress with polling.

## Messages

A2A messages are suitable for interactions that don't require long-running processing or complex state management. When A2A servers return a message, the contents are translated into the query response. Client-side accumulation of conversation context is not needed, and conversation context is ignored if sent to the server. Ark history can be used to track messages, but conversation history is not hydrated.

As a demonstration of A2A messages, you can install the [`mock-llm`](https://github.com/dwmkerr/mock-llm) service, which provides an 'echo' agent that echos input messages:

```bash
# Install mock-llm with A2A agents enabled.
helm install mock-llm oci://ghcr.io/dwmkerr/charts/mock-llm \
  --set ark.a2a.enabled=true

# Wait for the A2A agents to become available.
kubectl get agents
# NAME                    MODEL   AVAILABLE   AGE
# echo-agent                      True        10s
# countdown-agent                 True        10s
# message-counter-agent           True        10s
```

Query the `echo-agent`:


```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: echo-example
spec:
  target:
  - name: echo-agent
    type: agent
  input: "Testing incoming messages"

  # When sending an openai messages array, only the final user message is sent
  # to the A2A server.
  # type: messages
  # input:
  #   - role: user
  #     content: "First message"
  #   - role: assistant
  #     content: "First response"
  #   - role: user
  #     content: "Follow up question"
```

Response:

```yaml
status:
  phase: done
  responses:
    - content: "Testing incoming messages"
      target:
        name: echo-agent
        type: agent
```

View the A2ATask that was created for this query:

```bash
# List A2ATasks for the query
kubectl get a2atasks -l ark.mckinsey.com/query-name=echo-example

# View the completed A2ATask details
kubectl describe a2atask $(kubectl get a2atasks -l ark.mckinsey.com/query-name=echo-example -o name)
```

The A2ATask will show phase `completed` with the message history and artifacts from the A2A protocol interaction.

## Artifacts

An A2A agent can return multiple text artifacts from a single task. Ark preserves all of them, but `status.response.content` and `status.response.raw` expose them differently, and picking the wrong field is a common source of confusion.

Ark turns each text artifact into its own assistant message, in artifact order, deduplicated by artifact name or ID. That message list is what you get in `status.response.raw`. `status.response.content` is the final assistant message, so for a multi-artifact reply it holds only the last artifact.

Given an agent that returns three artifacts named `alpha`, `beta` and `gamma`:

```bash
kubectl apply -f - <<'EOF'
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: multi-artifact-example
spec:
  target:
  - name: multi-artifact-agent
    type: agent
  input: "return three sections"
EOF

kubectl wait --for=condition=Completed query/multi-artifact-example --timeout=60s
```

`content` carries the last artifact only:

```bash
kubectl get query multi-artifact-example -o jsonpath='{.status.response.content}'
# SECTION_GAMMA
```

`raw` carries all three, in order:

```bash
kubectl get query multi-artifact-example -o jsonpath='{.status.response.raw}' | jq -r '.[].content'
# SECTION_ALPHA
# SECTION_BETA
# SECTION_GAMMA
```

This is intended behavior, not truncation. `content` mirrors OpenAI chat-completions semantics, where the answer is the final assistant message, and many consumers rely on it being a single answer rather than a concatenation.

Choose the field to match what you need:

- **One canonical answer**: read `status.response.content`. Correct for single-artifact agents and for agents whose last artifact is the summary.
- **Every artifact**: read `status.response.raw` and iterate the message array. Required for agents that split their output across artifacts.

If your consumer needs a single string containing everything, join the `raw` messages yourself, or have the agent return one artifact whose text already combines the sections.

See [issue #3180](https://github.com/mckinsey/agents-at-scale-ark/issues/3180) for the discussion behind this contract.

## Stateful Messages

Ark sends `spec.conversationId` to all execution engines as the A2A `contextId`. This is the primary mechanism for conversation threading — use it for multi-turn interactions with any engine (completions or named).

The pattern:
- **Input**: Set `spec.conversationId` when creating a query
- **Output**: Read the returned conversation ID from `status.conversationId` (or `status.a2a.contextId`) after query completes

> **Advanced: sub-agent context override.** The `ark.mckinsey.com/a2a-context-id` annotation sets the A2A contextId for the *second hop* — when the completions engine dispatches to sub-agents. For most use cases, `spec.conversationId` is sufficient.

The `message-counter-agent` can be used to test this functionality. Send an initial message:

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: count-messages
spec:
  target:
  - name: message-counter-agent
    type: agent
  input: "First message"
```

Track the context ID generated when the query completes:

```bash
# Wait for query to complete
kubectl wait --for=condition=Completed query/count-messages --timeout=30s

# View the response
kubectl get query count-messages -o jsonpath='{.status.response.content}'
# 1 message(s) recieved

# Extract the context ID from status
CONTEXT_ID=$(kubectl get query count-messages -o jsonpath='{.status.a2a.contextId}')
echo "Context ID: ${CONTEXT_ID}"
```

Messages sent with this context ID are associated with a single conversation via the A2A server:

```bash
# Send 10 messages with the same context ID
for i in {1..10}; do
  kubectl apply -f - <<EOF
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: count-messages-${i}
  annotations:
    ark.mckinsey.com/a2a-context-id: "${CONTEXT_ID}"
spec:
  target:
  - name: message-counter-agent
    type: agent
  input: "Message ${i}"
EOF
  kubectl wait --for=condition=Completed query/count-messages-${i} --timeout=30s
done

# Check the final count
kubectl get query count-messages-10 -o jsonpath='{.status.response.content}'
# 11 message(s) recieved
```

Team members are the exception to the "conversation history is not hydrated" rule above. When an A2A agent runs as a member of a [Team](/user-guide/teams), Ark renders the accumulated team transcript into the message it sends, so the member sees earlier members' turns without relying on server-side retention. Member calls carry whatever `contextId` the query carries — none, unless the query sets `ark.mckinsey.com/a2a-context-id` — so if you do thread a context and the server retains history, those turns arrive both in the message and in the server's own state.
