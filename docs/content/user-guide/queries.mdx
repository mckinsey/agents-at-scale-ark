# Run queries / chat with agents and teams

A `Query` is how you actually run work on an Ark resource. You pick a target (an agent, a team, a model, or a tool), provide an input, optionally pass parameters or set a `conversationId` for multi-turn memory, and Ark executes it and returns the response. The full schema reference (every field, every phase) lives at [Reference → Query](/reference/resources/query). This page walks you through the two ways to run queries — chat from the dashboard, or apply YAML / use the CLI — plus parameters, conversations, and troubleshooting.

## Minimum viable query

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: hello
spec:
  input: "What is the capital of France?"
  target:
    type: agent
    name: my-agent
```

That's enough to apply. The controller validates that the target exists, sends the input to it, and writes the response to `status.response.content` when `status.phase` becomes `done`.

## Run a query

### Via Dashboard

The dashboard has two surfaces for queries — an embedded **chat panel** that lives next to every agent and team page, and a top-level **Queries** tab for creating named, parametric, multi-turn queries you want to keep around.

#### Embedded chat (fastest path)

1. Launch the dashboard: `ark dashboard`.
2. Go to **Agent Builder → Agents** (or **Teams**) in the left nav and open any resource.
3. Type into the chat panel on the right and hit **Send**.

The panel streams the response inline. While a turn is in flight the **Send** button becomes a **Stop** button you can use to cancel. For teams, the panel also surfaces selector choices (`<selector> chose <speaker>`) and a `Maximum turns reached (N)` badge when `maxTurns` is hit. Each conversation has a **New Chat** action that starts a fresh `conversationId`.

#### Create Query form

1. Go to **Agent Builder → Queries** in the left nav and click **New Query**.
2. Fill the three columns:

| Column | Field | Notes |
| --- | --- | --- |
| **Query** | **Name** | Optional. Auto-generated if blank. |
| | **Svc. Account** | Optional Kubernetes ServiceAccount for RBAC during execution. |
| | **Target** | Required (unless you use a Selector). Pick an agent, team, model, or tool. |
| | **Session ID** | Optional. Groups related queries for tracking and telemetry. |
| | **Conversation ID** | Optional. Threads multiple queries into one conversation; auto-generated when memory is set and you don't provide one. |
| **Configuration** | **Timeout** | Default `5m`. Format: `30s`, `5m`, `1h`. |
| | **TTL** | How long the Query resource sticks around after completing. Default comes from `ArkConfig/default.spec.queryTTL` (720h fallback). |
| | **Memory** | Optional. Pick a `Memory` resource so the conversation history is persisted under `conversationId`. |
| | **Streaming** | When the agent/team supports streaming, the chat panel streams partial chunks. |
| | **Parameters** | Free-form `name → value` pairs that fill `{{.name}}` placeholders in the input (and in agent prompts that declare a `queryParameterRef`). |
| **Advanced Settings** | **Selector** | Optional label selector — alternative to **Target** for fan-out across multiple resources matching labels. |
| | **Cancel** | Yes/No toggle that patches `spec.cancel: true` to stop a running query (also see [Cancel a running query](#cancel-a-running-query) below). |

3. Type the **Input** in the bottom panel, then hit **Execute Query**.

The right side shows the **Status & Results** column with Phase, the assistant Response, and Token Usage. The embedded chat panel on every agent / team page (covered in the previous section) is the equivalent surface for unnamed conversational queries.

### Via kubectl

For a one-off query that runs immediately:

```bash
ark query agent/my-agent "What is the capital of France?"

# Or the longer subcommand form (also works for teams, models, tools)
ark agents query my-agent "What is the capital of France?"
ark teams query my-team "Summarise the news on EVs."
ark query model/default "Explain rate limiting."
```

For a query you want to persist (resource lifecycle, status fields, multi-turn memory), apply a `Query` resource:

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: hello-q1
spec:
  input: "What is the capital of France?"
  target:
    type: agent
    name: my-agent
EOF

# Watch it complete.
kubectl get query hello-q1 -w

# Read the assistant's final message.
kubectl get query hello-q1 -o jsonpath='{.status.response.content}'

# Or the full conversation as a JSON array of messages.
kubectl get query hello-q1 -o jsonpath='{.status.response.raw}'
```

`kubectl get queries` shows `Type` / `Phase` / `Duration` / `Age` columns.

## Templated input + parameters

You can templatise the input with Go template syntax and pass values inline or from a ConfigMap / Secret:

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: weather-q1
spec:
  input: "What's the weather in {{.city}}?"
  parameters:
    - name: city
      value: "Boston"
    - name: api_key
      valueFrom:
        secretKeyRef:
          name: weather-api
          key: token
  target:
    type: agent
    name: weather-agent
```

Parameters are resolved server-side before the input reaches the target. If the agent's own prompt or system message declares a `queryParameterRef`, the same parameter values flow through there too — see [Agents → Parameters in the prompt](/user-guide/agents#parameters-in-the-prompt) for that wiring.

## Multi-turn conversations

To keep context across queries, set the same `conversationId` on every query in the chain:

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: greet-q1
spec:
  input: "Hi, my name is Alice."
  conversationId: chat-alice-001
  target:
    type: agent
    name: assistant
---
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: greet-q2
spec:
  input: "What's my name?"
  conversationId: chat-alice-001
  target:
    type: agent
    name: assistant
```

The second query sees the first one's exchange and answers "Alice". The dashboard chat panel handles this for you — every message you send in the same chat reuses the same `conversationId` until you click **New Chat**.

The completions executor resolves history through a `Memory` resource. **If you don't set `spec.memory`, it tries to use a `Memory` named `default` in the same namespace**, falling back to a no-op store if that doesn't exist. Most Ark installs ship a `default` Memory backed by the in-cluster broker, which is why the example above works without setting `memory` explicitly. Set `spec.memory.name` only when you want to pin to a non-default store.

## Fan-out with a label selector

Use `selector` instead of `target` to broadcast the same input to every matching resource. Each match produces a response.

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: panel-q1
spec:
  input: "Should we ship this feature next sprint?"
  selector:
    matchLabels:
      role: reviewer
```

The admission webhook requires **either** `target` **or** `selector` — applying neither is rejected.

## Cancel a running query

Set `spec.cancel: true` on the Query (via `kubectl edit` or a patch) and the controller transitions it to `phase: canceled`:

```bash
kubectl patch query slow-q1 --type='merge' -p='{"spec":{"cancel": true}}'
kubectl get query slow-q1 -o jsonpath='{.status.phase}'   # canceled
```

The dashboard chat panel's **Stop** button does the same thing for embedded chats.

## Inspect, list, delete

```bash
ark queries list                       # quick list
kubectl get queries                    # full kubectl view (Type/Phase/Duration/Age)
kubectl describe query hello-q1        # conditions + token usage
kubectl get query hello-q1 -o yaml     # everything

kubectl delete query hello-q1
kubectl delete queries --field-selector=status.phase=done   # bulk-delete completed queries
```

Token usage lands at `.status.tokenUsage.{promptTokens,completionTokens,totalTokens}` — handy for spot-checking costs.

## Features only available in YAML

The dashboard's Create Query form covers name, target, session/conversation IDs, timeout/TTL, memory, parameters, and selectors. These features are only configurable via the `Query` YAML for now:

- **`spec.overrides`** — inject HTTP headers when the query's target calls its model or any MCP server. Useful for upstream API gateways. See [Overrides](/user-guide/overrides).
- **`spec.cancel: true`** — programmatic cancellation. The dashboard exposes Stop on the embedded chat; explicit Query resources require a patch.

## Troubleshooting

**`kubectl apply` rejected by the admission webhook.** Webhook errors come back in the apply output before the resource exists:

- **`target or selector must be specified`** — every query needs one of the two. Set `spec.target` or `spec.selector`.
- **`target references agent 'X' does not exist in namespace 'Y'`** — apply the referenced Agent/Team/Model/Tool first.
- **`target: unsupported type 'X'`** — `target.type` must be one of `agent`, `team`, `model`, `tool`.

**`phase: error`.** Read the response content for the underlying error:

```bash
kubectl get query my-q -o jsonpath='{.status.response.content}'
```

Common causes:

- A2A / executor returned a 500 — usually the agent's tools or model are misconfigured; check `kubectl describe agent <name>` for the model/tool resolution path.
- Timeout exceeded — bump `spec.timeout` (default `5m`); see the [Reference → Timeout Behavior](/reference/resources/query#timeout-behavior).

**Query never starts (`phase: pending` forever).** The controller couldn't dispatch — usually because the controller pod is restarting or the ark-completions executor isn't reachable. `kubectl get pods -n ark-system` and check `ark-controller` + `ark-completions` are both `Running`.

**Want streaming chunks instead of one final message?** The chat panel streams natively when streaming is enabled on the agent. For external clients see [Developer Guide → Streaming queries](/developer-guide/queries/streaming).

**Need to debug what the agent actually saw?** `kubectl get query <name> -o jsonpath='{.status.response.raw}'` returns the full message array (system prompt + user + assistant + any tool calls and results), which is what the dashboard's **Debug** tab renders.
