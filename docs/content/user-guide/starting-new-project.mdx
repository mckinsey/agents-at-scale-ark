# Starting a New Agentic Project

This guide walks you through laying out a new agent project on top of Ark and testing it end to end. It assumes the [Quickstart](/quickstart) is done — Ark is running and `ark`, `kubectl` work against your cluster.

## How Projects Relate to Ark

**Ark provides the runtime, not the place where you build agents.** Your project — agents, tools, teams, queries — lives in its own directory (and usually its own git repository), separate from the Ark install. This separation lets:

- Multiple teams build their own agent projects against the same Ark
- Project YAML evolve under version control independently of Ark itself
- Platform upgrades happen without forcing agent rewrites

There is no required directory layout. The conventions below are a starting point — use whatever shape your team prefers.

## Prerequisites

- Ark installed on your cluster
- `kubectl` configured for that cluster
- A model named `default` available (`ark models create default`)

Verify:

```bash
ark --version
kubectl get pods -n ark-system
kubectl get models
```

## Step 1: Lay Out a Project Directory

A small, conventional layout:

```bash
mkdir -p my-agents/{agents,teams,queries,tools,mcp-servers}
cd my-agents
```

That's all the structure you need. From here, every resource is a YAML file you write and apply with `kubectl`.

## Step 2: Create Your First Agent

```bash
cat > agents/customer-support.yaml <<'EOF'
apiVersion: ark.mckinsey.com/v1alpha1
kind: Agent
metadata:
  name: customer-support
spec:
  description: Handles customer inquiries and support tickets
  modelRef:
    name: default
  prompt: |
    You are a helpful customer support assistant.
    Help users with their questions and issues professionally and efficiently.
EOF

kubectl apply -f agents/customer-support.yaml
kubectl get agent customer-support
```

Wait for the agent to reach `ready`:

```bash
kubectl get agent customer-support -o jsonpath='{.status.phase}'
# ready
```

## Step 3: Add a Tool

Tools give agents capabilities beyond pure text. This example wraps the National Weather Service HTTP API:

```bash
cat > tools/get-forecast.yaml <<'EOF'
apiVersion: ark.mckinsey.com/v1alpha1
kind: Tool
metadata:
  name: get-forecast
spec:
  type: http
  description: Get weather forecast for a specific location and time period
  inputSchema:
    type: object
    required: ["office", "gridX", "gridY"]
    properties:
      office:
        type: string
        description: "Weather office identifier (e.g., TOP)"
      gridX:
        type: integer
        description: "Grid X coordinate"
      gridY:
        type: integer
        description: "Grid Y coordinate"
  http:
    url: https://api.weather.gov/gridpoints/{office}/{gridX},{gridY}/forecast
EOF

kubectl apply -f tools/get-forecast.yaml
```

See the [Tools guide](/user-guide/tools) for MCP, builtin, and agent-as-tool variants.

## Step 4: Build a Team

Teams let multiple agents collaborate. Pick a strategy — each one expects a slightly different shape.

### Sequential

Members run in declared order, passing context forward:

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Team
metadata:
  name: support-team-sequential
spec:
  description: Triage, then specialist
  strategy: sequential
  maxTurns: 5
  members:
    - type: agent
      name: customer-support
    - type: agent
      name: order-tracker
    - type: agent
      name: escalation-handler
```

### Round-robin

Members take turns until `maxTurns` is reached:

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Team
metadata:
  name: support-team-roundrobin
spec:
  description: Each member contributes in turn
  strategy: round-robin
  maxTurns: 5
  members:
    - type: agent
      name: customer-support
    - type: agent
      name: order-tracker
```

### Graph

A custom workflow defined by edges. `maxTurns` and `graph.edges` are required:

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Team
metadata:
  name: support-team-graph
spec:
  description: Custom workflow
  strategy: graph
  maxTurns: 5
  members:
    - type: agent
      name: customer-support
    - type: agent
      name: order-tracker
    - type: agent
      name: escalation-handler
  graph:
    edges:
      - from: customer-support
        to: order-tracker
      - from: order-tracker
        to: escalation-handler
```

### Selector

A nominated agent decides which member runs next. `selector.agent` is required and refers to an Agent in the same namespace:

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Team
metadata:
  name: support-team-selector
spec:
  description: Selector agent picks the right specialist
  strategy: selector
  maxTurns: 5
  members:
    - type: agent
      name: customer-support
    - type: agent
      name: order-tracker
  selector:
    agent: planner-agent
    selectorPrompt: "Choose the best agent for: {{.Input}}"
```

Apply whichever strategy fits and check the team status:

```bash
kubectl apply -f teams/support-team-sequential.yaml
kubectl get team support-team-sequential
```

## Step 5: Add an MCP Server (Optional)

To expose external capabilities via the Model Context Protocol, declare an `MCPServer` resource pointing at a running MCP endpoint:

```bash
cat > mcp-servers/example.yaml <<'EOF'
apiVersion: ark.mckinsey.com/v1alpha1
kind: MCPServer
metadata:
  name: example-mcp
spec:
  address:
    value: "http://example-mcp.default.svc.cluster.local:8080/mcp"
  transport: http
  timeout: 1m
EOF

kubectl apply -f mcp-servers/example.yaml
```

For a fuller example including authentication and OAuth, see [MCP Servers](/user-guide/samples/mcp-servers).

## Step 6: Test with a Query

```bash
cat > queries/test-support.yaml <<'EOF'
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: test-support
spec:
  input: "I need help with my order #12345"
  target:
    type: agent
    name: customer-support
EOF

kubectl apply -f queries/test-support.yaml
```

Watch it complete and inspect the response:

```bash
kubectl get query test-support -w
# Phase progresses: pending -> running -> done

kubectl get query test-support -o jsonpath='{.status.responses[0].content}'
```

## Step 7: End-to-End Testing

### Option 1: A Bash Smoke Script

```bash
cat > test-workflow.sh <<'EOF'
#!/bin/bash
set -e

echo "=== Smoke testing the Ark workflow ==="
kubectl apply -f agents/
kubectl apply -f tools/
kubectl apply -f teams/

kubectl wait --for=jsonpath='{.status.phase}'=ready agent/customer-support --timeout=60s

kubectl apply -f queries/test-support.yaml
kubectl wait --for=jsonpath='{.status.phase}'=done query/test-support --timeout=120s

RESPONSE=$(kubectl get query test-support -o jsonpath='{.status.responses[0].content}')
if [ -z "$RESPONSE" ]; then
  echo "FAIL: empty response"
  exit 1
fi

echo "PASS"
echo "Response: $RESPONSE"
kubectl delete query test-support
EOF

chmod +x test-workflow.sh
./test-workflow.sh
```

### Option 2: Chainsaw (Recommended)

For declarative, repeatable tests, use [Chainsaw](https://kyverno.github.io/chainsaw/):

```yaml
apiVersion: chainsaw.kyverno.io/v1alpha1
kind: Test
metadata:
  name: customer-support-workflow
spec:
  steps:
    - name: apply-resources
      try:
        - apply:
            file: agents/customer-support.yaml
        - apply:
            file: queries/test-support.yaml

    - name: wait-for-agent-ready
      try:
        - assert:
            resource:
              apiVersion: ark.mckinsey.com/v1alpha1
              kind: Agent
              metadata:
                name: customer-support
              status:
                phase: ready

    - name: verify-query-done
      try:
        - assert:
            resource:
              apiVersion: ark.mckinsey.com/v1alpha1
              kind: Query
              metadata:
                name: test-support
              status:
                phase: done
                (length(responses) > `0`): true
                (length(responses[0].content) > `10`): true

    - name: cleanup
      try:
        - delete:
            ref:
              apiVersion: ark.mckinsey.com/v1alpha1
              kind: Query
              name: test-support
```

Run it:

```bash
chainsaw test --test-file chainsaw-test.yaml
```

## Step 8: Iterate

Add more agents the same way — one YAML per file:

```bash
# agents/order-tracker.yaml, agents/product-recommender.yaml, ...
kubectl apply -f agents/
```

Wire them into a richer team:

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Team
metadata:
  name: full-support-team
spec:
  description: Complete customer support workflow
  strategy: sequential
  maxTurns: 10
  members:
    - type: agent
      name: customer-support
    - type: agent
      name: order-tracker
    - type: agent
      name: escalation-handler
```

## Best Practices

### Organise by feature

Group everything for one feature under one directory:

```
my-agents/
├── features/
│   ├── customer-support/
│   │   ├── agents/
│   │   ├── tools/
│   │   ├── queries/
│   │   └── tests/
│   └── order-processing/
│       ├── agents/
│       ├── tools/
│       └── tests/
```

### Version control

```bash
git init
git add .
git commit -m "feat: initial Ark project setup"
```

### Per-environment overlays with Kustomize

```yaml
apiVersion: kustomize.config.k8s.io/v1beta1
kind: Kustomization
resources:
  - agents/
  - tools/
  - teams/
namespace: my-agents-prod
```

### Continuous testing in CI

```yaml
name: Test Ark Agents
on: [push, pull_request]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Setup K3s
        run: curl -sfL https://get.k3s.io | sh -
      - name: Install Ark
        run: ark install -y
      - name: Run Tests
        run: chainsaw test --test-dir tests/
```

## Troubleshooting

### Agent stuck before `ready`

```bash
kubectl describe agent customer-support
kubectl logs -n ark-system -l app=ark-controller
kubectl get models
```

### Query stuck

```bash
kubectl get query test-support -o yaml
kubectl get query test-support -o jsonpath='{.status.error}'
kubectl get events --field-selector involvedObject.name=test-support
```

### Tool returns nothing

```bash
kubectl get tool get-forecast
kubectl describe tool get-forecast
```
