# User authorised MCP servers

When several people share an Ark deployment, you often want calls to an external service to run **as the individual user**. This tutorial shows how, using the GitHub MCP server as the example: the server is registered once, and each query carries the user's own token via an **override**.

By the end you'll have:

- A GitHub `MCPServer` registered in the cluster.
- An agent that uses a GitHub tool.
- A personal Secret per user holding their GitHub token.
- Queries, from the dashboard chat and from the API, that authorise as different users by overriding the `Authorization` header per request.

## How per-user auth works

An `MCPServer` can carry static `spec.headers` (a shared token), or a bearer resolved from `spec.authorization.tokenSecretRef`. On top of either, an Agent or a Query can set `spec.overrides` with `resourceType: mcpserver` to inject or replace headers for that specific run. The headers merge with this precedence (last wins):

```
MCPServer.spec.headers  <  MCPServer.spec.authorization  <  Agent.spec.overrides  <  Query.spec.overrides
```

The `MCPServer`-level credential applies to both tool **discovery** and tool **calls**, so an agent can use the server with no override at all. A per-query `Authorization` override replaces it for that call — that's what makes the request "user authorised."

Each user keeps their token in a [personal Secret](/user-guide/secrets#personal-secrets). Only its owner sees it in the dashboard and `/v1/secrets`. Ark resolves it only from a header of a Query `mcpserver` override, and Ark API accepts that override only from the owner and only with a selector that picks one server by its name label.

## Prerequisites

- A working Ark cluster with a `default` model available (`kubectl get models`).
- A GitHub token per user. The remote GitHub MCP server (`https://api.githubcopilot.com/mcp/`) accepts a GitHub personal access token as a bearer token.
- Ark API and the dashboard running with single sign-on, so each user signs in as themselves. Personal Secrets need a signed-in user: with an API key or in `open` mode, creating one returns `403`. For a local cluster, `ENABLE_SSO=true devspace dev` starts Dex with two users, as described in [local development setup with Dex](/developer-guide/authentication#local-development-setup-with-dex).

## Step 1 — Register the GitHub MCP server

The MCP controller connects to the server, discovers its tools, and creates a `Tool` per function. It needs a token to do that — use a service/registration token here (any valid GitHub token works). This token is also the fallback for tool calls that carry no override, so scope it accordingly:

```bash
# Registration token: used for tool discovery, and for any call without an override.
kubectl create secret generic github-registration-token \
  --from-literal=token="Bearer $(gh auth token)"
kubectl label secret github-registration-token \
  ark.mckinsey.com/resource-type=secret ark.mckinsey.com/scope=shared
```

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: MCPServer
metadata:
  name: github
spec:
  address:
    value: "https://api.githubcopilot.com/mcp/"
  transport: http
  timeout: "30s"
  description: "Remote GitHub MCP server"
  headers:
    - name: Authorization
      value:
        valueFrom:
          secretKeyRef:
            name: github-registration-token
            key: token
    - name: User-Agent
      value:
        value: "ark-tutorial/1.0"
```

Ark labels every MCPServer with its own name, here `ark.mckinsey.com/name: github`, so a query override can pick this one server by name.

Apply it and wait for discovery:

```bash
kubectl apply -f github-mcp.yaml
kubectl get mcpserver github -o jsonpath='{.status.conditions[?(@.type=="Available")].message}'
# Successfully discovered 44 tools
```

The discovered tools are labelled with the server name (`mcp/server: github`):

```bash
kubectl get tools -l mcp/server=github
# github-get-me, github-get-file-contents, github-search-repositories, ...
```

## Step 2 — Create an agent that uses a GitHub tool

`github-get-me` returns the authenticated user — handy because the answer reveals *which* token authorised the call.

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Agent
metadata:
  name: github-agent
spec:
  prompt: |
    You answer questions about the user's GitHub account. Use the
    github-get-me tool to find the authenticated user, then state their login.
  tools:
    - type: mcp
      name: github-get-me
```

```bash
kubectl apply -f github-agent.yaml
```

## Step 3 — Each user stores their own token

Each user creates a personal Secret holding their token. Sign in to the dashboard as Alice, open **Secrets** and select **Add secret**:

- Name: `github`.
- Scope: **Personal**.
- Value: `Bearer ghp_alice_personal_access_token`.

The dashboard stores the value under the `token` key. Ark names the Secret `u-<owner>-github`, where `<owner>` is a hash of Alice's username, and the **Secrets** page shows it as `github` with that full name underneath. Bob does the same with his own token and gets a different full name. Neither of them sees the other's Secret.

## Step 4 — Chat with the agent as the user

As Alice, open a chat with `github-agent`. Above the message box sits the **MCP credentials** block, collapsed while it has no rows. Expand it, select **+** to add a row, and fill it in:

- MCP server: `github`.
- Header name: `Authorization`, the default.
- Secret: `github`, marked **Personal**.
- Key: `token`, the default.

Ask "Who am I on GitHub? Reply with just my login." The chat sends the row as an `mcpserver` override that selects `ark.mckinsey.com/name: github` and reads Alice's Secret, so the `github-get-me` call runs with her token and the agent answers with her login. Bob does the same with his own Secret, and the same agent answers as Bob, without re-registering the server.

The rows apply to every agent and team chat in the namespace, and the browser keeps them for Alice in that namespace. A server created before the upgrade and not updated since has no name label, shows **Needs name label** and cannot be picked. See [use personal secrets from the chat](/user-guide/secrets#use-personal-secrets-from-the-chat) for the cases where the chat blocks sending.

## Step 5 — Query as the user through the API

A front-end or service sends the same override through the [Ark API](/reference/ark-apis). Set the API address and an ID token for Alice, issued by your identity provider for the client that Ark API trusts:

```bash
ARK_API=http://ark-api.default.127.0.0.1.nip.io:8080
read -rs ALICE_TOKEN
```

Copy the full name of Alice's Secret from the **Secrets** page, then send the query. The `labelSelector` picks the `github` server by its name label:

```bash
curl -X POST "$ARK_API/v1/queries?namespace=default" \
  -H "Authorization: Bearer $ALICE_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "name": "who-am-i",
    "input": "Who am I on GitHub? Reply with just my login.",
    "target": { "type": "agent", "name": "github-agent" },
    "overrides": [
      {
        "resourceType": "mcpserver",
        "labelSelector": { "matchLabels": { "ark.mckinsey.com/name": "github" } },
        "headers": [
          {
            "name": "Authorization",
            "value": { "valueFrom": { "secretKeyRef": { "name": "u-0123456789abcdef-github", "key": "token" } } }
          }
        ]
      }
    ]
  }'
```

Replace `u-0123456789abcdef-github` with the full name you copied. The override block maps straight onto the `Query` spec. Once the query is done, read the result:

```bash
curl -s "$ARK_API/v1/queries/who-am-i?namespace=default" \
  -H "Authorization: Bearer $ALICE_TOKEN" | jq -r .status.response.content
# alice
```

Ark API accepts the query only because Alice owns the Secret. If Bob sends a query that references Alice's Secret, or Alice selects the server by anything other than its name label alone, Ark API returns `422` and creates nothing. Selecting by name keeps her token on that one server.

## Alternative — pass the token at request time

If you don't want a per-user Secret, the override header can read from a **query parameter**, so the token is supplied with the request:

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Query
metadata:
  name: who-am-i-param
spec:
  input: "Who am I on GitHub?"
  parameters:
    - name: githubToken
      value: "Bearer ghp_alice_personal_access_token"
  target:
    type: agent
    name: github-agent
  overrides:
    - resourceType: mcpserver
      headers:
        - name: Authorization
          value:
            valueFrom:
              queryParameterRef:
                name: githubToken
```

The parameter value is stored in the Query, so anyone who can read Queries in the namespace sees the token, and without a `labelSelector` the header goes to every MCP server the agent uses.

<Callout type="warning">
Whichever source you use, the token authorises real API calls — treat it like a credential. Prefer Secrets over inline `value`, and never put a token in an agent prompt or a Query `input` (it would become part of the model context). The `valueFrom.secretKeyRef` / `queryParameterRef` paths keep it out of the prompt.
</Callout>

## Verify it's the override doing the work

A quick way to prove the per-query token is what authorises the call: send a query whose override carries a **bad** token. The GitHub MCP connection fails, and the query ends in `error` — even though the server's registration token is valid:

```yaml
spec:
  input: "Who am I on GitHub?"
  target:
    type: agent
    name: github-agent
  overrides:
    - resourceType: mcpserver
      headers:
        - name: Authorization
          value:
            value: "Bearer ghp_not_a_real_token"
```

```bash
kubectl get query <name> -o jsonpath='{.status.phase}'              # error
kubectl get query <name> -o jsonpath='{.status.response.content}'   # MCP client creation failed
```

Replace it with a valid token and the same query succeeds — confirming the override header is what reaches GitHub.

## Where to set the override

- **On the Query** (shown above) — per request, per user. The most common choice for user-authorised access.
- **On the Agent** (`Agent.spec.overrides`) — every query through that agent uses the same token. Useful for a dedicated service agent, less so for per-user auth. An Agent override cannot reference a personal Secret.

Query overrides win over agent overrides, which win over the server's `spec.headers`.
