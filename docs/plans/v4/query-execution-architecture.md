# Modular Query Execution Architecture

## Response to Issue #1219

This design responds directly to the architectural discussion in [#1219](https://github.com/mckinsey/agents-at-scale-ark/issues/1219).

### drew-foxall's proposal

Drew proposed that every execution engine becomes an A2A server and the controller becomes an A2A client. A default engine ships with Ark. Tool execution stays in the controller via `input-required` callbacks.

**Where this design aligns:**
- Every execution engine is an A2A server. The controller dispatches via A2A. Agreed.
- A default engine ships with Ark — the Ark Execution Engine, bundled in the controller. Agreed.
- The ExecutionEngine CRD is the extension point. Agreed.
- Namespace-level engine deployment. Agreed.
- Explicit engine selection in the CRD, or namespace default. Agreed.

**Where this design differs:**
- Tool execution. Drew proposes tools stay in the controller for all engines via `input-required`. This design takes a different position: **external engines manage their own tools.** The Claude SDK Execution Engine runs Claude Code, which has its own tool system (Bash, Read, Write, Edit). The controller's ToolRegistry is only used by the Ark Execution Engine. The `input-required` pattern can be added later for engines that want controller-managed tools, but it's not the default.
- Team validation. Drew proposes replacing `validateNoMixedTeam()` with capability matching via Agent Cards. This design defers that — teams work today across engines because all engines return A2A responses. Advanced capability matching is a follow-up concern.

### havasik's "6 steps to scale" proposal

Havasik proposed a broader rearchitecture: immutable agents published by executor controllers, clients connecting directly to A2A endpoints, session management as K8s resources, and an Ark SDK for code-first agent implementations.

**Where this design aligns:**
- A2A Agent Cards for capability discovery. Agreed — engines expose `/.well-known/agent-card.json`.
- Executors are standalone services deployed per namespace. Agreed — this is exactly what the ExecutionEngine CRD represents.
- Ark SDK for building engines. Agreed as a direction — the `claude-code-agent` open-source project demonstrates this pattern today.

**Where this design defers:**
- Immutable agents generated by executor controllers. Not in this iteration. Agents remain user-defined K8s resources.
- Clients connecting directly to A2A endpoints. The controller remains the routing hub. Direct client connections are a future evolution.
- Session management as K8s resources (rewind, cancel, continue). Session lifecycle is engine-managed in this design. K8s-native session resources are a follow-up.

**Synthesis:** Drew's proposal is the implementation plan. Havasik's proposal is the roadmap. This design implements Drew's architecture while laying the foundation for havasik's steps.

## What is an Execution Engine?

An execution engine is a service that runs queries. It receives a query (via A2A protocol), executes it, and returns a response.

The **ExecutionEngine CRD** is a Kubernetes resource that acts as a named pointer. It stores an address — that's it. It doesn't contain execution logic. Think of it like an Ingress — it describes where traffic should go, not what happens when it gets there.

What the address points to varies:

- **The controller itself** — The Ark Execution Engine runs in-process. No separate Service or Deployment needed.
- **A Kubernetes Service** — An engine deployed as a Service + Deployment in a namespace.
- **An external URL** — An engine running outside the cluster entirely.

```
 ExecutionEngine CRD
 ┌──────────────────┐
 │ name: my-engine  │      can point to...
 │ address: ────────┼──▶  controller itself  (in-process, no separate service)
 │                  │──▶  K8s Service:8080   (Deployment in the namespace)
 │                  │──▶  https://ext.ai/a2a (external service)
 └──────────────────┘
       K8s CRD
    (the pointer)
```

The Ark controller reads the ExecutionEngine CRD to find the address. It sends queries to that address via A2A. What happens behind the address is the engine's business.

## Four Scenarios

### Scenario 1: The Ark Execution Engine (Default)

Out of the box, Ark ships with a built-in execution engine. This engine handles completions (the LLM agent loop), tool execution, and direct model calls. It runs inside the Ark controller process.

No ExecutionEngine CRD, Service, or Deployment needed. This is what Ark does today.

```
 ┌─────────────────────────────────────────────────────────────────┐
 │                    ARK CONTROLLER  (ark-system)                 │
 │                                                                 │
 │  Query CR ──▶ Query Controller ──▶ Resolve target               │
 │                                        │                        │
 │                         agent has no   │                        │
 │                         executionEngine│                        │
 │                                        ▼                        │
 │                          ┌──────────────────────────────────┐   │
 │                          │     Ark Execution Engine          │   │
 │                          │                                   │   │
 │                          │  ┌─────────────────────────────┐  │   │
 │                          │  │ prompt → LLM → tool calls   │  │   │
 │                          │  │ → execute tools → repeat    │  │   │
 │                          │  │ → final response            │  │   │
 │                          │  └─────────────────────────────┘  │   │
 │                          │                                   │   │
 │                          │  Supports:                        │   │
 │                          │  • OpenAI, Azure, Bedrock models  │   │
 │                          │  • MCP tools, inline tools        │   │
 │                          │  • Streaming responses            │   │
 │                          │  • Teams, memory                  │   │
 │                          └──────────────────────────────────┘   │
 │                                                                 │
 └─────────────────────────────────────────────────────────────────┘
```

The Ark Execution Engine is a module within the controller. It's the same code that runs today — the agent loop in `genai/agent.go:executeLocally()`. It calls LLM providers (OpenAI, Azure, Bedrock) via the completions API, executes tools via the ToolRegistry, and manages the prompt → model → tools → repeat cycle.

This engine is independently deployable. A cluster admin could package it as a standalone service and deploy it per namespace (Scenario 2). It's bundled in the controller for convenience.

### Scenario 2: Per-Namespace Completions Engine

An organization wants each namespace to run its own completions engine — for isolation, resource accounting, or custom configuration. The cluster admin deploys the same Ark Execution Engine code as a separate service in each namespace.

```
                                        NAMESPACE: team-alpha
                                        ┌─────────────────────────────────────┐
 ┌──────────────────────┐               │                                     │
 │ ARK CONTROLLER       │               │  ExecutionEngine CR                 │

 │                      │               │  address: completions-svc:8080      │
 │ Query Controller     │               │                                     │
 │   │                  │               │  ┌───────────────────────────────┐   │
 │   ▼                  │     A2A       │  │ Service + Deployment          │   │
 │ agent.executionEngine│──────────────▶│  │                               │   │
 │ = "completions"      │               │  │  ┌─────────────────────────┐  │   │
 │                      │               │  │  │ Ark Execution Engine    │  │   │
 │                      │               │  │  │ (standalone deploy)     │  │   │
 │                      │               │  │  │                         │  │   │
 │                      │               │  │  │ prompt → LLM → tools   │  │   │
 │                      │               │  │  │ → loop → response      │  │   │
 │                      │               │  │  └─────────────────────────┘  │   │

```

The agent's `spec.executionEngine.name` points to the `completions` ExecutionEngine in the namespace. The Ark controller resolves the address and sends the query via A2A. The per-namespace engine runs the same completions code, but in its own resource space.

```yaml
apiVersion: ark.mckinsey.com/v1
kind: ExecutionEngine
metadata:
  name: completions
  namespace: team-alpha
spec:
  address:
    value: "http://completions.team-alpha.svc:8080"
  description: "Per-namespace completions engine"
```

### Scenario 3: Claude SDK Execution Engine (Shared)

A team installs the Claude SDK Execution Engine from the marketplace. This engine wraps Claude Code behind an A2A server. All sessions share a single deployment — Claude Code processes run in-memory within the same pod.

This follows the pattern established by the [`claude-code-agent`](https://github.com/dwmkerr/claude-code-agent) open source project: an Express A2A server that spawns Claude Code CLI processes per message, using `--resume <sessionId>` for multi-turn conversations.

```
                                        NAMESPACE: team-alpha
                                        ┌─────────────────────────────────────┐
 ┌──────────────────────┐               │                                     │
 │ ARK CONTROLLER       │               │  ExecutionEngine CR                 │
 │ (ark-system)         │               │  name: claude-sdk                   │
 │                      │               │  address: claude-sdk-svc:8080       │
 │ Query Controller     │               │                                     │
 │   │                  │               │  ┌───────────────────────────────┐   │
 │   ▼                  │     A2A       │  │ Service + Deployment          │   │
 │ agent.executionEngine│──────────────▶│  │                               │   │
 │ = "claude-sdk"       │               │  │  ┌─────────────────────────┐  │   │
 │                      │               │  │  │ Claude SDK A2A Server   │  │   │
 │                      │               │  │  │                         │  │   │
 │                      │               │  │  │  Session A (in-memory)  │  │   │
 │                      │               │  │  │  ├─ claude --resume A   │  │   │
 │                      │               │  │  │  │                      │  │   │
 │                      │               │  │  │  Session B (in-memory)  │  │   │
 │                      │               │  │  │  ├─ claude --resume B   │  │   │
 │                      │               │  │  │  │                      │  │   │
 │                      │               │  │  │  Session N ...          │  │   │
 │                      │               │  │  └─────────────────────────┘  │   │
 │                      │               │  │                               │   │
 │                      │               │  └───────────────────────────────┘   │
 │                      │               │                                     │
 └──────────────────────┘               └─────────────────────────────────────┘
```

Each A2A message arriving at the Claude SDK server triggers a Claude Code CLI process. The server maintains an in-memory map of `contextId → claudeSessionId`. First message starts a fresh Claude Code process. Subsequent messages resume the session with `--resume`. The Claude Code process handles its own tools (Bash, Read, Write, Edit, Grep, Glob) — the Ark controller's ToolRegistry is not involved.

```yaml
apiVersion: ark.mckinsey.com/v1
kind: ExecutionEngine
metadata:
  name: claude-sdk
  namespace: team-alpha
spec:
  address:
    value: "http://claude-sdk.team-alpha.svc:8080"
  description: "Claude SDK execution engine (shared)"
```

This is simple to deploy and sufficient for light workloads. Sessions share the pod's resources. State is lost if the pod restarts.

### Scenario 4: Session-Isolated Claude SDK Execution Engine

For production workloads that need isolation between sessions — separate filesystem, separate resource limits, separate security contexts — the Claude SDK engine acts as a **router and scheduler**. Instead of running Claude Code in-process, it creates a dedicated pod per session.

```
                                        NAMESPACE: team-alpha
                                        ┌──────────────────────────────────────────────┐
 ┌──────────────────────┐               │                                              │
 │ ARK CONTROLLER       │               │  ExecutionEngine CR                          │
 │ (ark-system)         │               │  name: claude-sdk-isolated                   │
 │                      │               │  address: claude-router-svc:8080             │
 │ Query Controller     │               │                                              │
 │   │                  │               │  ┌────────────────────────────────────────┐   │
 │   ▼                  │     A2A       │  │ Service + Deployment                   │   │
 │ agent.executionEngine│──────────────▶│  │                                        │   │
 │ = "claude-sdk-       │               │  │  ┌──────────────────────────────────┐   │   │
 │    isolated"         │               │  │  │ Claude SDK Router               │   │   │
 │                      │               │  │  │                                  │   │   │
 │                      │               │  │  │  session map:                    │   │   │
 │                      │               │  │  │    session-A → pod-a2a-session-a │   │   │
 │                      │               │  │  │    session-B → pod-a2a-session-b │   │   │
 │                      │               │  │  │                                  │   │   │
 │                      │               │  │  │  new session? → create pod       │   │   │
 │                      │               │  │  │  existing?    → route to pod     │   │   │
 │                      │               │  │  │  idle?        → delete pod       │   │   │
 │                      │               │  │  └──────────┬─────────┬─────────────┘   │   │
 │                      │               │  │             │         │                 │   │
 │                      │               │  └─────────────┼─────────┼─────────────────┘   │
 │                      │               │                │         │                     │
 │                      │               │     ┌──────────▼───┐  ┌──▼─────────────┐      │
 │                      │               │     │ Pod: session-a│  │ Pod: session-b │      │
 │                      │               │     │              │  │                │      │
 │                      │               │     │ Claude Code  │  │ Claude Code   │      │
 │                      │               │     │ A2A Server   │  │ A2A Server    │      │
 │                      │               │     │              │  │               │      │
 │                      │               │     │ Workspace PVC│  │ Workspace PVC │      │
 │                      │               │     │ (10Gi)       │  │ (10Gi)        │      │
 │                      │               │     └──────────────┘  └───────────────┘      │
 │                      │               │                                              │
 └──────────────────────┘               └──────────────────────────────────────────────┘
```

The engine's Deployment runs a **router** — an A2A server that doesn't execute queries itself. Instead it:

1. **New session arrives** (no existing pod for this session ID): Creates a pod from a pod template, waits for it to become ready, routes the A2A message to the pod.
2. **Existing session** (pod already running): Routes the A2A message directly to the existing pod.
3. **Session idle** (no messages for N minutes): Deletes the pod and its workspace PVC.
4. **Session explicitly closed**: Deletes the pod and workspace.

Each session pod runs the same Claude Code A2A server from Scenario 3, but in isolation. Each pod gets:
- Its own CPU and memory limits
- Its own workspace PVC (persistent storage for files created during the session)
- Its own security context (can run as a different user, with different capabilities)
- Its own Claude Code process with `--resume` for multi-turn

This is the most sophisticated form of an execution engine. It functions as a **mini-scheduler within a namespace** — creating and managing pods the way a Deployment controller does, but with session affinity instead of replica count.

The engine's `config` holds session lifecycle settings. Pod specifications come from **PodTemplate resources** in the namespace — standard Kubernetes objects that engines reference when creating session pods.

```yaml
apiVersion: ark.mckinsey.com/v1
kind: ExecutionEngine
metadata:
  name: claude-sdk-isolated
  namespace: team-alpha
spec:
  address:
    value: "http://claude-router.team-alpha.svc:8080"
  description: "Claude SDK with per-session isolation"
  config:
    isolation: "per-session"
    defaultPodTemplate: "claude-standard"
    sessionIdleTimeout: "30m"
    sessionMaxDuration: "4h"
```

Agents can specify which pod template the engine should use via annotations. The engine receives the full agent spec via A2A metadata, reads the annotation, and creates a pod from the matching PodTemplate. This enables **specialized pods per agent** — a code reviewer gets a lightweight pod, a deep researcher gets GPU and extra memory.

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Agent
metadata:
  name: gpu-researcher
  annotations:
    executors.ark.mckinsey.com/claude-sdk-isolated.podTemplate: "gpu-heavy"
spec:
  executionEngine:
    name: claude-sdk-isolated
  prompt: "You are a deep researcher with GPU access."
---
apiVersion: ark.mckinsey.com/v1alpha1
kind: Agent
metadata:
  name: code-reviewer
  annotations:
    executors.ark.mckinsey.com/claude-sdk-isolated.podTemplate: "lightweight"
spec:
  executionEngine:
    name: claude-sdk-isolated
  prompt: "Review code for correctness and style."
```

The PodTemplates themselves are standard Kubernetes resources managed by the cluster admin:

```yaml
apiVersion: v1
kind: PodTemplate
metadata:
  name: gpu-heavy
  namespace: team-alpha
template:
  spec:
    containers:
      - name: engine
        image: ghcr.io/mckinsey/ark-claude-sdk:latest
        ports:
          - containerPort: 8080
            name: a2a
        resources:
          requests: { cpu: "4", memory: "8Gi", nvidia.com/gpu: "1" }
          limits:   { cpu: "8", memory: "16Gi", nvidia.com/gpu: "1" }
    nodeSelector:
      gpu: "true"
    tolerations:
      - key: "nvidia.com/gpu"
        operator: "Exists"
        effect: "NoSchedule"
---
apiVersion: v1
kind: PodTemplate
metadata:
  name: lightweight
  namespace: team-alpha
template:
  spec:
    containers:
      - name: engine
        image: ghcr.io/mckinsey/ark-claude-sdk:latest
        ports:
          - containerPort: 8080
            name: a2a
        resources:
          requests: { cpu: "500m", memory: "512Mi" }
          limits:   { cpu: "1", memory: "1Gi" }
```

Each session pod runs an A2A endpoint — the same Claude Code A2A server from Scenario 3. The router forwards A2A messages to the session pod, which handles them the same way a shared engine would. The pod template just determines the resources and environment the session gets.

If an agent doesn't specify a pod template annotation, the engine falls back to the `defaultPodTemplate` from its config.

## The ExecutionEngine CRD

The existing CRD is a named pointer to a service. It is namespace-scoped.

```yaml
apiVersion: ark.mckinsey.com/v1
kind: ExecutionEngine
metadata:
  name: claude-sdk
  namespace: team-alpha
spec:
  # Where the engine's A2A server listens
  address:
    value: "http://claude-sdk.team-alpha.svc:8080"
    # Can also reference a Secret, ConfigMap, or ServiceRef

  description: "Claude SDK execution engine"

  # Engine-specific configuration (new, optional)
  # Passed to the engine via A2A metadata. Controller does not interpret it.
  config:
    isolation: "per-session"
    maxTurns: "50"
    thinking: "enabled"

status:
  lastResolvedAddress: "http://claude-sdk.team-alpha.svc:8080"
  phase: Ready
```

### What the controller does with an ExecutionEngine

1. **ExecutionEngine Controller** watches ExecutionEngine CRDs. It resolves the `spec.address` (which can be a direct value, a Secret reference, a ConfigMap reference, or a ServiceRef) and writes the resolved URL to `status.lastResolvedAddress`. That's all it does.

2. **Query Controller** reads the resolved address at query time. It sends an A2A message containing the agent's prompt, tools, history, and the engine's config map. The engine handles it.

The controller doesn't know what framework runs behind the address. It doesn't know about Claude Code, LangChain, or CrewAI. It just sends A2A and gets a response.

### New field: `spec.config`

A `map[string]string` of engine-specific configuration. Passed to the engine via A2A metadata alongside the agent config, tools, and history.

Examples:

```yaml
# Completions engine
config:
  maxTurns: "10"

# Claude SDK engine (shared)
config:
  thinking: "enabled"
  maxTurns: "50"
  timeout: "3600"

# Claude SDK engine (session-isolated)
config:
  isolation: "per-session"
  defaultPodTemplate: "claude-standard"
  sessionIdleTimeout: "30m"
  sessionMaxDuration: "4h"
```

The controller does not validate or interpret these values. The engine validates them when it receives the first query and returns an A2A error if something is wrong.

### Per-agent overrides via annotations

Agents can override engine defaults and specify infrastructure requirements via annotations. The controller sends both the engine's `spec.config` and the full agent spec (including annotations) via A2A metadata. The engine reads the annotations and acts on them.

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Agent
metadata:
  name: deep-researcher
  annotations:
    executors.ark.mckinsey.com/claude-sdk.maxTurns: "100"
    executors.ark.mckinsey.com/claude-sdk.thinking: "extended"
    executors.ark.mckinsey.com/claude-sdk.podTemplate: "gpu-heavy"
spec:
  executionEngine:
    name: claude-sdk
  prompt: "You are a deep researcher."
```

Behavioral annotations (`maxTurns`, `thinking`) override engine config. Infrastructure annotations (`podTemplate`) tell session-isolated engines which PodTemplate to use when creating the session pod. The engine merges them — agent annotations override engine defaults.

## How Routing Works

```
 Query CR created
   │
   ▼
 Query Controller resolves target (agent / team / model / tool)
   │
   ├── target is model or tool
   │   └── Ark Execution Engine handles it (always, in-process)
   │
   ├── target is team
   │   └── Team orchestrator runs in-process
   │       Each member routes independently (back to this decision tree)
   │
   └── target is agent
       │
       ├── Agent has spec.executionEngine.name?
       │   └── YES: resolve the named ExecutionEngine CRD
       │           read status.lastResolvedAddress
       │           send query via A2A
       │
       └── NO: Ark Execution Engine handles it (in-process)
```

Three rules:

1. **Explicit wins.** If an agent sets `spec.executionEngine.name`, the query goes to that engine. Always.
2. **Built-in is the fallback.** If no engine is specified, the Ark Execution Engine (in the controller) handles it. This is what Ark does today.
3. **Model and tool targets are always in-process.** Direct model calls (`target.type: model`) and direct tool calls (`target.type: tool`) are handled by the Ark Execution Engine. They don't route to external engines.

### How agents reference engines

```yaml
apiVersion: ark.mckinsey.com/v1alpha1
kind: Agent
metadata:
  name: code-reviewer
spec:
  executionEngine:
    name: claude-sdk        # routes to the claude-sdk ExecutionEngine in the same namespace
  prompt: "Review code."
---
apiVersion: ark.mckinsey.com/v1alpha1
kind: Agent
metadata:
  name: chatbot
spec:
  modelRef: { name: gpt-4o }
  prompt: "Chat with users."
  # No executionEngine → Ark Execution Engine handles it
```

## Teams

Teams work across engines because all engines return A2A responses.

```
 Team: project-team (selector strategy)
   │
   ├── Selector agent (Ark Execution Engine, in-process)
   │   Picks the next member based on conversation state
   │
   ├── code-reviewer (Claude SDK engine, via A2A)
   │   Returns text response via A2A
   │
   ├── researcher (Responses API engine, via A2A)
   │   Returns text response via A2A
   │
   └── chatbot (Ark Execution Engine, in-process)
       Returns text response directly
```

The team orchestrator always runs in the Ark Execution Engine (in-process). It dispatches to each member independently. Members on external engines receive their queries via A2A and return responses via A2A. The orchestrator passes text-only history between members — tool call details and engine-internal artifacts are not portable across engines.

## What the Claude SDK Engine Looks Like

Inspired by the [`claude-code-agent`](https://github.com/dwmkerr/claude-code-agent) open source project, the Claude SDK Execution Engine is:

1. **An A2A server** built on the A2A SDK (`@a2a-js/sdk` or Go equivalent)
2. **Exposes an Agent Card** at `/.well-known/agent-card.json` declaring capabilities (streaming, skills)
3. **Spawns Claude Code CLI** per message: `claude -p "user text" --output-format stream-json --resume <sessionId>`
4. **Streams responses** — Claude Code's NDJSON output is parsed and published as A2A StatusUpdate events
5. **Manages sessions** — maps A2A `contextId` to Claude Code `sessionId` for multi-turn conversations
6. **Runs init scripts** — per-session initialization (MCP servers, plugins, CLAUDE.md) via `.init-session.sh`

In the **shared** deployment (Scenario 3), all of this runs in a single pod. Sessions share memory. State is lost on pod restart.

In the **session-isolated** deployment (Scenario 4), the A2A server in the main pod acts as a router. It creates a separate pod per session, each running its own Claude Code A2A server with its own workspace volume. The router manages pod lifecycle: creation on new sessions, routing on existing sessions, cleanup on idle timeout.

### Marketplace installation

```bash
helm install claude-sdk ark-marketplace/executor-claude-sdk \
  --namespace team-alpha \
  --set config.isolation=per-session \
  --set config.workspaceSize=10Gi
```

This creates:
- A Deployment (the Claude SDK A2A server)
- A Service (exposes it on port 8080)
- An ExecutionEngine CRD (the named pointer)

## Migration

### What exists today

- ExecutionEngine CRD with `spec.address` and `spec.description`
- Three execution paths: built-in (no engine ref), named engine (A2A), A2A direct (annotations)
- A2A is the only protocol between controller and engines (PR #1215 merged, HTTP removed)

### What changes

1. **Add `spec.config`** (`map[string]string`, optional) to ExecutionEngine CRD. Additive, backward-compatible.
2. **Add RBAC** for QueryReconciler to list ExecutionEngines (needed if namespace default is added later).
3. **Ship Claude SDK engine** as a marketplace Helm chart.
4. **Agents reference engines** via existing `spec.executionEngine.name` field. No new fields needed.

### What does NOT change

- The ExecutionEngine CRD stays in its current API group. No API version migration.
- The Ark Execution Engine (built-in) works exactly as it does today.
- Agents without `spec.executionEngine` continue to use the built-in engine.
- A2A remains the only protocol.

## Design Principles

1. **An execution engine is a service.** The ExecutionEngine CRD is a pointer to that service. The service runs the agent loop.

2. **The Ark controller ships with an execution engine.** It handles completions, tools, models, and teams. It works out of the box.

3. **External engines are A2A servers.** Deploy them per namespace. Point an ExecutionEngine CRD at them. Agents reference them by name.

4. **Engines manage themselves.** The controller sends A2A and gets a response. It doesn't know about pods, sessions, workspaces, or Claude Code processes. The engine handles all of that internally.

5. **Complexity lives in engines, not the controller.** A simple engine runs queries in-memory. A sophisticated engine schedules pods per session. The controller doesn't change.

6. **Namespace-scoped.** Each namespace controls its own engines. No cluster-scoped resources.
