## 3. Migrate Hooks and Services

Each hook file is one unit of work: update its query keys, its service functions, and their call sites together, then verify the file references no client default params. Follow `lib/services/marketplace-hooks.ts`.

- [x] 3.1 `models-hooks.ts` + `models.ts` — migrate first as the reference implementation, and confirm its list, detail, create, update, and delete flows before continuing — established the two conventions the rest of the migration follows: the namespace is the **first** parameter of every service function, and it is appended as the **last** element of every query key. Last matters: `useUpdateModelById` invalidates `[GET_MODEL_BY_ID_QUERY_KEY, model.id]`, which only still matches because the namespace sits after the id
- [x] 3.2 `agents-hooks.ts`, `teams-hooks.ts`, `tools-hooks` callers, `secrets-hooks.ts` — `secrets-hooks.ts` needed more than the pattern: its optimistic update uses `getQueryData`/`setQueryData`/`cancelQueries`, which match **exactly**, not by prefix, so each had to take the namespace or the optimistic write would have silently targeted a key that no longer existed. `tools.ts` also lost its `namespace?` field on the create payload, replaced by the argument

- [x] 5.1 Manually switch between two namespaces with visibly different resources on the models, agents, and memory screens, confirming no stale data appears during or after the switch — **verified on the models screen against a live minikube**, run through a local dashboard (`localhost:3000`) talking to a local ark-api so the request identity was the developer's kubeconfig rather than the RBAC-limited `ark-api-sa`. `?namespace=default` renders `default` and `test-model-mock`; switching to `?namespace=ark-system` renders the empty state with `models?namespace=ark-system` returning 200, and neither `default` model appears at any point; switching back to `?namespace=default` renders both again.   **Not covered:** the agents and memory screens named in the task, and a switch performed while a request was already in flight. Both are asserted by `namespace-scoped-data.test.tsx` (the in-flight case with a deferred promise) but were not exercised by hand.

## 6. Merging `main`

`main` advanced by ~70 commits while this change was open. Some of them changed the same surface and extended the migration; the merge is recorded here because the work list in section 3 no longer describes the finished state on its own.

- [x] 6.1 **#2948 server-side pagination.** Ten list functions moved from `apiClient.get` to `fetchAllPages<T>(endpoint, params, client)`, which follows `continue_token` until the server reports the last page. Each now passes `{ namespace }` as that helper's `params` argument, so **every page of a paginated list is fetched for the same namespace** — the helper spreads `params` into each iteration's query alongside `limit` and `continue`. Had the namespace been dropped here, page 1 would have been correct and pages 2+ would have resolved against the pod namespace. Pinned by a new scenario in the spec. Affected: `agents`, `teams`, `models`, `memories`, `mcp-servers`, `tools`, `a2a-servers`, `a2a-tasks`, `memory.getMemoryResources`, and the five list calls in `export.fetchAllResources`

It merged without conflict, so nothing flagged it; once the singleton was deleted its requests would have carried no namespace at all and resolved in the pod namespace. Migrated to the section 3 convention: namespace first on all six of `getAll`/`get`/`create`/`update`/`delete`/`getReferences`, namespace last on all three keys, `enabled: Boolean(namespace)` on all three queries.
