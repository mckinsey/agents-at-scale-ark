## Why

Ark ships Argo Workflows as a first-class service and the dashboard already lists, visualises, and runs `WorkflowTemplate` resources at `/workflow-templates`. There is currently **no in-product way to author a new template** — users must hand-write Argo YAML and `kubectl apply`. This locks the feature behind YAML literacy and excludes the non-technical users (typically PMs) that the workflows tab is meant to serve.

A previous evaluation of visual workflow editors (Flowify) found them too feature-thin to fill the gap. Rather than continue searching for a click-and-drag editor, this change adds a conversational authoring experience — modelled on Figma Make — where a non-technical user prompts their way to a runnable workflow.

A complete authoring experience is not just creation: users must also be able to **open an existing template and refine it**, and to **hand-edit the generated YAML** when they want precise control the chat can't easily express. The user is a co-editor, not just a prompter — so the agent must always be working against the *current* draft, including edits the user made by hand and changes that have not yet been saved.

The fit is unusually clean: the dashboard already renders any workflow YAML through `WorkflowDagViewer` (no Argo round-trip required), so the LLM's generated YAML renders in the same canvas the user will see after Save (the preview updates when the agent finishes responding, not mid-stream).

The other piece that makes conversational authoring viable is the [`kubernetes-mcp-server`](https://github.com/containers/kubernetes-mcp-server). **Its role in this feature is to facilitate authoring workflow templates that interact with Ark primitives** — the generated templates do not run in a vacuum, they submit Ark `Query` resources against real targets. The read-only MCP server exposes generic `resources_list` / `resources_get` tools that let the author Agent list the user's **existing query targets** (the `Agent`, `Model`, and `Team` resources a `Query` can address) directly from the cluster. So when a template embeds a query step, the author can ground it in a target that actually exists and is available, rather than inventing one. The same tools let the author list existing `WorkflowTemplate` resources to riff on. No bespoke Ark MCP tools are needed — the generic resource-listing tools cover every Ark kind.

There is also a gap on the workflow-authoring side itself: there is **no Ark-native way to submit a `Query` from an Argo workflow**. Every sample today (`query-fanout-template.yaml`, `a2a-arithmetic-workflow.yaml`, `weather-workflow-template.yaml`) re-emits the same inline recipe — `kubectl apply` a `Query`, `kubectl wait --for=condition=Completed`, `jq` the result, exit non-zero on error. This boilerplate is the single most error-prone thing the author Agent and the user have to reproduce. Shipping it as one reusable, well-tested template closes the gap for hand-written workflows and gives the author Agent a canonical building block to reference instead of regenerating the recipe each time.

## What Changes

This change has four parts that fit together — a dashboard authoring UI, the Agent that drives it, a reusable query template that Agent (and hand-written workflows) build on, and the production deployment of the MCP server the Agent grounds itself through:

- **New dashboard pages** — `/workflow-templates/new` and `/workflow-templates/[id]/edit`: a two-pane chat + live DAG / editable-YAML experience for authoring and refining `WorkflowTemplate` resources.
- **The author Agent and its prompt** — `argo-make-author`, an Ark `Agent` whose manifest (spec + system prompt) is bundled in the dashboard. Its prompt carries the schema crib, the grounding/fail-fast rules, and the canonical recipes; the dashboard dispatches each authoring turn to it.
- **The `ark-query` Argo template** — a reusable `WorkflowTemplate` that submits an Ark `Query`, waits for completion, and returns structured outputs. It ships in the argo-workflows Helm chart.
- **Production deployment of the `kubernetes-mcp-server`** — a Helm umbrella chart so the read-only MCP server ships with real Ark installs, not just `devspace dev`.

**How they relate:** the dashboard pages host the chat that dispatches to the author Agent; the author Agent grounds itself on the user's existing Ark resources through the `kubernetes-mcp-server` (so the MCP deployment is its runtime dependency) and writes query steps by referencing the `ark-query` template via `templateRef` (which hand-written workflows can reuse too). The detailed changes for each part follow.

### Conversational authoring

- Add a new dashboard route `/workflow-templates/new` with a two-pane layout:
  - **Left:** chat panel reusing the existing chat/session infrastructure
  - **Right:** live preview with two tabs — `WorkflowDagViewer` (read-only DAG) and an **editable YAML editor**. The existing `CodeViewer` is a read-only `react-syntax-highlighter`, so authoring introduces an editable editor for the YAML tab (`CodeViewer` stays the read-only renderer elsewhere)
- Make a single **`draftYaml` buffer the source of truth** for the route. Both writers feed it — the agent (its latest fenced ` ```yaml ` block) and the user (manual edits in the editable YAML tab) — and the preview, Save, and agent-grounding all read from it. This replaces the earlier model where the agent's last message was the source of truth
- **Ground the agent on the live draft.** Track the draft and the agent's last emitted block; on each user turn, if they diverge (the user hand-edited the YAML, or an existing template was just loaded), prepend the current draft to the user's input so the agent edits the real current state. When they match, send the user's text alone — history already carries the YAML. The agent always replies with a full replacement block. No backend change; the draft never leaves the browser until Save
- Add an **edit entry point** for existing templates: a dedicated `/workflow-templates/[id]/edit` route (the `[id]` segment is the template `metadata.name`, matching the existing detail route) plus an "Edit" button on the template detail page. The edit route reuses the **same two-pane authoring experience** as `/workflow-templates/new` — identical chat panel, DAG/editable-YAML preview, `draftYaml` source-of-truth, agent grounding, and "New conversation" control — differing only in how the draft is seeded and how Save behaves. It seeds `draftYaml` via the existing `workflowTemplatesService.getYaml(name)` (with the agent's last block unset, so the first turn grounds the agent)
- Add a "New conversation" control inside the route (explicit only — never automatic) so a single session can host multiple authoring conversations
- On Save: add a create/overwrite method to `workflowTemplatesService`. A new template is **created** with a POST through the existing `/api/v1/resources/apis/argoproj.io/v1alpha1/WorkflowTemplate` passthrough (the same endpoint `run()` already POSTs to); an overwrite is an **in-place update (PUT)** through a new generic resource-update endpoint on the same passthrough (`PUT /api/v1/resources/apis/{group}/{version}/{kind}/{resource_name}`). Then navigate to the template's detail page.
  - **New-template Save:** detect a name collision **client-side** via the existing `workflowTemplatesService.list` (the dashboard already lists templates — no API change), and prompt to overwrite if the name is taken
  - **Edit-mode Save:** overwrite the same name silently (that's the intent), with "Save as new name" offered as a secondary action
- Ground the author Agent on the user's catalogue via the **`kubernetes-mcp-server`** (deployed by a separate change) — its generic `resources_list` tool lists `Agent`, `Model`, `Team`, and `WorkflowTemplate` resources by `apiVersion`/`kind`. This is what lets the author write a query step against a target the user actually has: when the user asks for a template that queries a given target, the author lists that kind to confirm the target exists and is available before emitting YAML that references it. No bespoke Ark MCP tools are added; the Agent references the existing `MCPServer` registration for `kubernetes-mcp-server` in its `spec.tools`. Read-only access is sufficient — every write the feature performs (creating the `WorkflowTemplate` on Save, creating the author Agent on Install) goes through the ark-api resources passthrough, not the MCP server
- **Install the author Agent from the dashboard, not `kubectl`.** Keep the canonical `argo-make-author` `Agent` manifest (spec + system prompt) as a bundled artifact **in the dashboard** — it is consumed only by the dashboard, so there is no reason to serve it from `ark-api`. The one-click "Install author agent" button (shown when the agent is missing) stamps the configured name onto that bundled manifest and creates the Agent in the selected namespace through the **existing resources passthrough** — no new ark-api endpoint. The Agent's system prompt:
  - **Documents how to list each Ark primitive via the `kubernetes-mcp-server`** — the exact `resources_list` call per kind, so the model does not have to guess the `apiVersion`/`kind`:
    - Agents → `resources_list` with `apiVersion: ark.mckinsey.com/v1alpha1`, `kind: Agent`
    - Models → `resources_list` with `apiVersion: ark.mckinsey.com/v1alpha1`, `kind: Model`
    - Teams → `resources_list` with `apiVersion: ark.mckinsey.com/v1alpha1`, `kind: Team`
    - Workflow templates → `resources_list` with `apiVersion: argoproj.io/v1alpha1`, `kind: WorkflowTemplate`

    scoped to the current namespace — Ark query targets are namespace-local (a `Query` can only address an `Agent`/`Model`/`Team` in its own namespace; `QueryTarget` has no namespace field), so there is no reason to list other namespaces — with instructions to read only the fields it needs (name, key spec fields, status phase) and ignore the rest
  - **Verifies query targets exist and are available — once per target:** when the user asks for a template that queries a target, the author lists the target's kind via `resources_list` and confirms the named target is present (and not in a failed/unavailable status) before emitting a query step that references it. Verification happens **the first time a target is mentioned in the conversation only** — once verified, the author does not re-verify the same target on later turns
    - **Loading an existing template does not trigger verification:** when the author opens an existing `WorkflowTemplate` to edit, it does **not** verify the targets already referenced in that template. It only verifies a target the **first time the user mentions it** in the conversation
    - **Resolving inexact names:** the listing is also used to resolve the exact target name when the user does not give one (e.g. "the weather agent" → `agent/weather`). If the author is **100% sure** of the match, it uses the resolved name. If it is **not certain** the guess is correct, it does **not** guess — it asks the user to confirm which target they meant from the listed candidates
  - Refuses to invent resources that aren't in the returned list (fail-and-tell-user) — replying with the available alternatives and asking which to use
  - Teaches embedding Ark queries inside Argo steps by **referencing the shipped `ark-query` template** (below) via `templateRef`, with the inline `kubectl apply` recipe retained as a fallback few-shot example
- Output is restricted to `kind: WorkflowTemplate` for v1. The natural follow-on output kinds are `CronWorkflow` (scheduled runs) and a one-shot `Workflow` (run-now, no reusable template) — both deferred to later versions (see Out of scope)

### Ark-native query template

- Ship a reusable `WorkflowTemplate` (`ark-query`) **as a managed resource in the argo-workflows Helm chart** (`services/argo-workflows/chart/templates/`) so it is installed automatically whenever Ark-with-Argo is installed — both via `devspace` (which deploys the chart as a dependency when `ENABLE_ARGO=true`) and via the production Helm install. It submits an Ark `Query`, waits for completion, and returns its result. Workflows reference one canonical, tested template via `templateRef` instead of re-emitting the query-and-wait recipe. The step uses the existing `alpine/k8s` image (`kubectl` + `jq`):
  - **Inputs:**
    - *Required:*
      - `target` — `type/name` notation matching the ark CLI (e.g. `agent/weather`, `model/default`, `team/research`)
      - `input` — the prompt; mirrors `spec.input`
    - *Optional* (drawn from `QuerySpec`):
      - `timeout` — default `5m`; also bounds the `kubectl wait`
      - `ttl`
      - `parameters` — JSON array merged into `spec.parameters` for `{{.param}}` templating
      - `session-id`
      - `memory`
      - `query-name` — else generated from the workflow/pod
      - `service-account`
  - **Outputs:**
    - `response` — the final `status.response.content`
    - `query-json` — the full Query object (for downstream steps that need token usage, target, etc.)
    - `phase` — `done` / `error`
    - `conversation-id` — `status.conversationId`
  - **Multiple team-member messages:** the Query CR exposes only the final assistant message in `status.response.content` (per-member turns live in the broker/memory keyed by `conversationId`, not in the CR). v1 outputs the final content plus the full Query JSON; the `conversation-id` output is the seam for a follow-up broker-backed transcript step
  - **Error handling:** the step always writes its output files *before* exiting — even on failure — so `continueOn: {failed: true}` consumers and Argo exit-handlers can still read `phase` / `response` / `query-json`. It exits `0` on `done` and non-zero on `error` or a wait-timeout / non-`done` phase, so the Argo node is marked Failed and `retryStrategy` / `continueOn` integrate naturally

### Production deployment of the kubernetes-mcp-server

The separate change that introduces `kubernetes-mcp-server` only wires it into the local `devspace dev` stack. Because this feature depends on it at runtime (the author Agent grounds itself through it), this change adds a **production Helm path** so the server ships with a real Ark install, not just dev:

- Add a `services/kubernetes-mcp-server/chart/` umbrella chart following the existing `services/argo-workflows/chart/` pattern: it declares the upstream `oci://ghcr.io/containers/charts/kubernetes-mcp-server` chart (v0.1.0) as a Helm dependency and layers Ark-specific values — `config.read_only: true`, read-only RBAC scoped to the install namespace, and the `localhost-gateway` `HTTPRoute` (Ingress disabled) — matching the dev configuration.
- Wire the chart into the standard service install path (`manifest.yaml` + `build.mk` so `make services` offers it, and the `deploy` workflow packages and pushes it to the OCI chart registry alongside the other service charts).
- The Ark `MCPServer` registration that points the cluster at this server is owned by the kubernetes-mcp-server change, not here; the production chart deploys the same server that registration targets.

## Capabilities

### New Capabilities
- `argo-make-authoring`: Conversational authoring of Argo `WorkflowTemplate` resources from natural-language prompts, with a DAG preview that updates when the agent finishes responding (and live for manual edits), editable YAML, editing of existing templates, and Ark-resource-grounded composition kept in sync with the user's current (possibly hand-edited, unsaved) draft
- `argo-query-template`: A reusable Argo `WorkflowTemplate` that submits an Ark `Query` and returns its result, shipped as a managed resource in the argo-workflows Helm chart (installed on every Ark-with-Argo install, via both `devspace` and production Helm), giving workflows an Ark-native way to run a query with structured outputs and Argo-integrated error handling
- `kubernetes-mcp-server-deployment`: A production Helm umbrella chart for `kubernetes-mcp-server`, wrapping the upstream OCI chart with read-only config and Ark-specific RBAC/routing, so it ships with real installs and not just `devspace dev`

### Modified Capabilities
- `ark-api`: Adds a generic resource **update (PUT)** endpoint to the resources passthrough (Save uses it to overwrite a template in place). No argo-make-specific endpoint — the author-agent manifest is bundled in the dashboard, and Agent creation reuses the existing resources passthrough
- `dashboard-workflow-templates`: Adds "New" and "Edit" entry points with chat-driven authoring — editable YAML, live DAG preview, and overwrite-on-save for edits — alongside the existing list and detail views, plus a one-click install for the author Agent when it is missing in the current namespace

## Impact

- **kubernetes-mcp-server (Helm):** New `services/kubernetes-mcp-server/chart/` umbrella chart wrapping the upstream `oci://ghcr.io/containers/charts/kubernetes-mcp-server` (v0.1.0) with read-only config, namespace-scoped read-only RBAC, and the `localhost-gateway` `HTTPRoute`, plus `manifest.yaml` / `build.mk` to wire it into `make services` and the `deploy` chart-publish workflow. No bespoke Ark MCP tools — grounding uses the server's generic `resources_list`.
- **ark-api (Python):** No argo-make-specific endpoint — the author-agent manifest lives in the dashboard. The only change is a generic resource **update** endpoint (`PUT /api/v1/resources/apis/{group}/{version}/{kind}/{resource_name}`) added to the resources passthrough so Save can overwrite a template in place; it mirrors the existing create/delete handlers and replaces the earlier DELETE + POST approach. Agent creation (Install) and template create/load reuse the existing passthrough (`POST` / `GET`).
- **argo-workflows chart (Helm/YAML):** One new chart-managed template under `services/argo-workflows/chart/templates/` (e.g. `ark-query-template.yaml`): the `ark-query` reusable `WorkflowTemplate`, installed with the chart so it is present on every Ark-with-Argo install — both `devspace` (chart deployed as a dependency when `ENABLE_ARGO=true`) and the production Helm install / OCI-published chart. The author Agent is **not** part of the chart — its manifest is bundled in the dashboard (above) and installed from there.
- **ark-dashboard (TypeScript):** New `/workflow-templates/new` and `/workflow-templates/[id]/edit` routes and supporting components, plus an "Edit" button on the template detail page. Introduces a new editable YAML editor component (the existing `CodeViewer` is a read-only `react-syntax-highlighter`), a `draftYaml` buffer that is the route's source of truth, and a small client-side grounding helper (diverge-check + input prefix). Dispatches authoring turns to the configured author Agent (`NEXT_PUBLIC_ARGO_MAKE_AUTHOR_AGENT`, default `argo-make-author`) in the currently-selected namespace; when that agent is absent, shows a one-click "Install author agent" button (reads the dashboard-bundled manifest, stamps the configured name, then creates the Agent via the existing resources passthrough) and otherwise degrades to a working manual YAML editor. Bundles the canonical `argo-make-author` manifest (spec + system prompt) as a static artifact — the single source of truth for the prompt. Reuses `chatService`, `conversationsService`, `agentsService` (`getByName` for the existence check), `WorkflowDagViewer`, `useNamespacedNavigation`, and `workflowTemplatesService` (`getYaml` for load). Template load goes through the existing `/api/v1/resources/.../WorkflowTemplate` passthrough (`getYaml`); save uses POST to create and the new resources **update (PUT)** endpoint to overwrite, via a save method added to `workflowTemplatesService`. Name-collision detection on a new-template Save is **client-side** via the existing `workflowTemplatesService.list`.
- **Tests:** Unit tests for the YAML extraction logic, the draft-grounding diverge-check, the missing-agent gating, the install helper (stamps the configured name onto the dashboard-bundled manifest), and the new resources update (PUT) endpoint (in-place replace); chainsaw e2e tests that exercise (a) the full author → save → run loop using mock-llm, (b) installing the author Agent from the dashboard into a namespace that lacks it, (c) loading an existing template, hand-editing the YAML, and confirming the agent's next turn is grounded on the edit, and (d) the `ark-query` template against an agent and a team target, asserting outputs on success and a Failed node with readable outputs on a query error.
- **Out of scope for v1:** a workflow-lint step (whether an MCP tool the author calls or a dashboard-side pre-Save check), `CronWorkflow` / one-shot `Workflow` output, canvas direct-manipulation (DAG click-to-edit), starter-prompt gallery, template versioning, a server-side draft store and the agent-callable draft-inspection tool it would enable (prefix-injection covers grounding for now), a broker-backed per-member transcript output for team queries (the `conversation-id` output is the seam), upgrading an already-installed author Agent to the latest bundled prompt (install is create-if-missing for v1), and a dashboard UI to choose a different author Agent (config-only for v1). Tracked as follow-ups.
